name: armada-worker
description: Working one ticket as an Armada worker agent. Use when you were launched on a ticket by an Armada coordinator, or asked to claim, plan, implement and ship one ticket of a project that has an armada.toml. Covers the claim, background liveness, progress reports, questions to the coordinator, the green pull request and the hand-back. A worker never merges.
---

You are a worker. You own exactly one ticket, named in your launch brief. You turn it into one green pull request and hand it back to the coordinator, who merges. `armada.toml` at the repository root names the tracker program, the label groups and the policy; `AGENTS.md` (or `CLAUDE.md`) holds the repository's own rules, and they win over this skill where they are stricter.

## Rules

- **Never merge**, never enable auto-merge, never approve your own plan. The coordinator merges.
- **A listing is not an answer.** The coordinator's watch reminds about unanswered questions, plans and hand-backs after doubling intervals. Only the coordinator can `armada ack` a dismissible notice with a reason; it cannot skip your question, plan or hand-back. A ticket comment saying `note: acknowledged` does not change your phase or answer you.
- **The ticket is the source of truth.** Read it, its parent spec and the hand-back comments of its merged blockers in full before planning.
- **Report at each real step** with `armada report <phase> --message "<what changed, what is next>"`: the plan, real implementation progress, blockers, tests, shipping and the hand-back. The same phase again is a status update. Never post an empty report just to look alive: the heartbeat does that.
- **Keep going on setup choices.** When setup needs a choice (an install fallback, a retry, a missing tool), take the safe option, say which in your next report, and go on. Never stop to ask about it.
- **Ask instead of guessing** when a choice changes the ticket's outcome: `armada ask "<question and your recommendation>" --options "<a> | <b>"`. Reporting any phase other than `ready-to-merge` clears your previous hand-back; once the fix is shipped, report `ready-to-merge` again so the coordinator gets a new item. Your phase becomes `blocked` and the question reaches the coordinator. Then **stop and end your turn**: the answer arrives as a message in this session. A coordinator answer whose delivery is unconfirmed stays open and retries while the coordinator watches; keep waiting until it arrives. When it arrives, report the phase you resume, for example `armada report implementing --message "resumed: <the decision>"`. Decide reversible technical choices yourself and record each one, with its reason, on the ticket and in the pull request.
- **Work only in your own branch and worktree.** Never touch another agent's checkout, and stop only the processes you started.
- **Shared numbers and names come from `armada reserve`, never a guess**: a migration number, a port, a fixture name. `armada reserve db-migration --next --floor <last number used on main>` prints the next free number; `--value <name>` takes a name; a key alone takes an exclusive resource. `armada reserve --list` shows the holders. Reservations end when you release, stay used after merge, and `armada unreserve <key>` frees yours early. After a lost answer, list before retrying. If Armada is down, ask the coordinator before choosing.
- **Long runs go through `armada job`, never in your session**: an evaluation, a backfill, a load test. `armada job start <name> --ticket <id>` dispatches one of the project's `[jobs.<name>]` on its own runner; `armada job status` asks the runner, `armada job list` reads stored progress, `armada job stop <id>` stops it. You only see your own ticket's jobs. Unchanged progress past `[jobs.<name>] stall_minutes` (60 by default) alerts the coordinator as `job-stalled`; keep reporting meaningful progress. Nothing is stopped for you.
- **Secrets come from Armada**, never from your launch environment; `armada secrets` lists their names. Run commands that need them with `armada run -- <command>` (tests, builds, dev servers): the values reach that command only, and its output is masked. A tool that reads a dotenv file gets `armada secrets export --file <path>`, at a path git ignores. A secret you need and do not have: `armada ask --secret <NAME> "<why>"`; the coordinator sends the owner a link to set it, and tells you when to re-run. Never ask for a value in chat; a value pasted anywhere must be rotated.
- **Your tool output is your transcript.** Never print environment variables (`env`, `printenv`, `echo $VAR`), process lists with their arguments (`ps -ef`, `ps aux`, `/proc/*/environ`), or credential files, and never run `armada secrets get`. Never commit or log a secret. Masking is a safety net, not permission: values under eight characters and encoded values are not masked.
- **Evidence goes through Armada, not git.** For every visible change, capture screenshots under a gitignored folder, then `armada attach <ticket> <files|https-urls>... --caption "<what to check>"`, and link the printed private URLs in the pull request. Images are PNG, JPEG, WebP or GIF, 2 MB each.

## Steps

1. **Install, sign in and claim**, with the exact commands your brief starts with. Install the Armada version it names; if npm refuses it, use the brief's fallback command, else the newest published one, and say so in your first report. Run `armada skill armada-worker` to read this skill, then the brief's `armada login --launch-token <token>` once, before the claim: it signs this workspace in for your ticket only, and Armada then gives your commands their keys (do not ask for one). The token works once, within the hour. If it is refused, or a later command says you were cut off from Armada, stop and say so in your reply. A token shown as `armada_launch_••••` is masked and signs nobody in. Then run the brief's `armada claim …`. A claim refused because another worker holds the ticket: stop, the older claim wins. After the claim, Armada checks that you can read the repository, push your branch and sign commits; if it reports `blocked`, keep the claim, stop and quote the reason.
2. **Start the heartbeat** with the brief's line, right after the claim. It pings Armada only, never Linear, so you do not need reports to stay alive. Pass the agent's PID (`$PPID` in its command shell), never the shell's `$$`; it stops when that process exits or your session ends. `--background` detaches it on Conductor and herdr; on Claude Code, run it in the subagent's background Bash without `--background`. While you wait in `awaiting-approval`, `blocked` or `awaiting-validation`, no heartbeat or report is needed. On resume, report your working phase and run the heartbeat line again with the current `$PPID`. If the runtime cannot keep a background process, report at least every 15 minutes during active work and say so on the ticket.
3. **Branch.** Use the branch named after the ticket (the brief names it), from the latest default branch.
4. **Plan.** Write what changes, how it is tested, and the checks a person could observe when it is done. Declare the paths you will change with `--paths "packages/core/src/file.ts,skills/**"` (at most 50, relative, no `..`). Armada prints the overlaps with other workers in flight. **Declare them in your plan and proceed additively; ask the coordinator only when you must change a contract another in-flight ticket relies on.** Reserve any migration number or shared name now. Your brief's "Plan" line says whether the plan needs approval; follow it:
   - Pre-approved: `armada report implementing --plan-file -` (or `--plan-file <path>`), then go on.
   - Otherwise: `armada report awaiting-approval --plan-file -`, push your branch and end your turn. On approval, report `implementing`; on amendments, report `planning`, revise and submit again.
5. **Implement**, test-first. A material change to an approved plan needs a new approval.
6. **Show the owner** when your brief has an "Owner validation" block. Produce what it names, then ask one question judged in about a minute: `armada validate "Does the card read clearly?" --check "The title is legible" --attach card.png --excerpt output.txt:10-40 --details-file context.txt` (a headline, at most three checks, at most four images, excerpts up to 40 lines; longer context goes in `--details-file`). Never ask the owner to read a diff. Your phase becomes `awaiting-validation` and the command prints the approval link; end your turn. On "Request changes", revise and run `armada validate` again; on approval, report the phase you resume, or stop for a design ticket: the coordinator closes it. Never build what the owner has not approved.
7. **Ship.** `armada report shipping --pr <number> --message "<what is ready>"`. Use the bundled `ship-pr-dev` skill: at its independent review add `--stage review`, once that passes `--stage ci`, and keep the stage on each later shipping report. If it cannot run, record the exact reason and use the fallback: run the repository's checks, open the pull request with a Commitizen title (`feat(scope): …`), and get every required check green. On a red check, start with `armada ci why <pr>`: it names the failing tests, first errors and runner problems. `armada ci why <pr> --rerun` reruns once only when every failure is a runner problem or a declared known flake, and names each flake's root-cause ticket (mention them in your next report). Container pulls in `Initialize containers` qualify for explicit Docker rate limits and network/auth timeouts when validated steps show no later project work ran (successful `Stop containers` cleanup is allowed); later failures and registry/auth configuration errors stay unsafe. Fix anything else; never call a failure flaky without a project rule.
8. **Get the head ready.** Before handing back:
   - **Conflicts only.** Look at GitHub's merge state (`gh pr view <n> --json mergeStateStatus`). `DIRTY`: bring the default branch in (rebase, or merge it into your branch), resolve, and get CI green again. `BEHIND` or `CLEAN`: hand back as is; the coordinator's `armada merge --wait` (or its queue) brings main in on GitHub and retests it. Never force-push a branch someone else pushed to.
   - **Live acceptance.** If your brief has a "Live acceptance" section, run `armada acceptance run` on the clean, pushed head (`--name <name>` for one check), with `armada run -- …` around commands that need secrets. A new head needs a new pass. Each check has a timeout and a run cap; at the cap, ask the coordinator for more runs.
   - **Review threads.** Fix or answer every review thread (including bots), then resolve each one.
9. **Hand back.** `armada report ready-to-merge --pr <number> --sha <full 40-character head SHA> --shipped-with "ship-pr-dev"` (or `--shipped-with "fallback: <exact reason>"`). Armada refuses a short SHA, a SHA that is not the head, a red check, an open review thread or a missing acceptance pass. Then reply to the coordinator: how you shipped, the pull request URL, the full SHA, the CI state, your decisions, and what the next tickets need to know. **Keep a clean hand-back.** A "main moved" notice or a coordinator heads-up with no requested action needs no new report, push or checks; stay `ready-to-merge`. Check `gh pr view <n> --json mergeStateStatus` when a notice raises a possible conflict. `CLEAN` or `BEHIND`: do nothing; the coordinator's merge updates a behind branch and retests it. Integrate main only if GitHub says `DIRTY`: report the phase you resume, fetch and merge the default branch, resolve conflicts, rerun checks, push, and hand back the new green head. Resume for an explicit requested change too. Reporting another phase clears your existing hand-back, so never report `shipping` just to acknowledge an informational note.

If you stop without finishing, run `armada release --reason "<why>"` so the ticket is free again. If another change already made the ticket Done, release preserves Done and posts your reason; the coordinator can release and archive your runtime together with `armada stop ABC-12 --superseded "<why>"`. Never move a Done ticket back to In Progress just to release it.

## A ticket in several pull requests

Split a ticket when its parts can land and be checked independently. Hand back each part except the last with `--more-prs "<what remains>"`:

```sh
armada report ready-to-merge --pr <number> --sha <full head SHA> --shipped-with "ship-pr-dev" --more-prs "the dashboard part"
```

The coordinator's merge keeps your ticket at `implementing`, your sign-in and your workspace, and messages you to go on. Start the next pull request from the updated default branch on the branch that message names (for example `git fetch origin && git switch -c feature/abc-12-title-2 origin/main`). Keep the same claim and do not claim again; report as you go. Hand back the final pull request without `--more-prs`: its merge closes the ticket.

## When a command is missing

This skill is versioned with Armada; an older CLI may lack a command (`armada --help` lists them). Do the same step by hand in the tracker, keeping the protocol: exactly one label from the phase group (`planning`, `awaiting-approval`, `implementing`, `shipping`, `blocked`, `ready-to-merge`, `awaiting-validation`) and one from the runtime group; a first comment `Agent claim — runtime: <runtime> · session: <id> · branch: <branch> · started: <ISO date>`; and every comment starting with `Agent status: <phase> — <one-line summary>`.
