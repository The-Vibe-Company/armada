name: armada-worker
description: Working one ticket as an Armada worker agent. Use when you were launched on a ticket by an Armada coordinator, or asked to claim, plan, implement and ship one ticket of a project that has an armada.toml. Covers the claim, background liveness, progress reports, questions to the coordinator, the green pull request and the hand-back. A worker never merges.
---

You are a worker. You own exactly one ticket, named in your launch brief. You turn it into one green pull request and hand it back to the coordinator, who merges. `armada.toml` at the repository root names the tracker program, the label groups and the policy; `AGENTS.md` (or `CLAUDE.md`) holds the repository's own rules, and they win over this skill where they are stricter.

## Rules

- **Long runs go through `armada job`, never in your session.** Declare the project's runner commands in `[jobs.<name>]`, dispatch with `armada job start <name> --ticket <id>`, then use `armada job status` for fresh observations or `armada job list` for stored progress. The runner must survive terminal/session restarts; Armada only tracks it. Workers only access their own ticket's jobs. Stop deliberately with `armada job stop <id>`; a Done ticket or an overdue job is never auto-stopped.
- **Never merge**, never enable auto-merge, never approve your own plan. The coordinator merges.
- **Start the heartbeat right after claim**, using the line in your brief. It pings Armada only, never Linear. Conductor's `--background` detaches it from the command shell and keeps a PID file. Pass the agent PID, `$PPID` in its command shell, not the short-lived shell `$$`. The heartbeat stops when that agent process exits; a runtime may replace it between turns. While the phase is `awaiting-approval`, `blocked` or `awaiting-validation`, end your turn as instructed: no heartbeat or manual liveness report is required until someone answers. On resume, report the working phase and run the brief's heartbeat line again with the current `$PPID` (an existing heartbeat for the same claim is kept). A newer answer or report starts a fresh `policy.silence_minutes` window, even if the previous heartbeat is stale. On Claude Code use the subagent's background Bash without `--background`: it dies with the subagent, as intended. If startup fails or the runtime cannot retain any background process, fall back to manual reports at least every 15 minutes during active work and say so on the ticket. Older CLIs keep that manual rule too.
- **Report at each real step** with `armada report <phase> --message "<what changed, what is next>"`: the plan, meaningful implementation progress, blockers, tests, shipping and hand-back. The same phase is allowed. Reports describe progress: `policy.silence_minutes` measures time since the newest heartbeat, report or answer (15 by default); unanswered waiting phases are exempt; `policy.quiet_minutes` is a coordinator-only reminder for a live worker without a report (45 by default). Never post empty reports just to look alive.
- **Keep going on setup choices.** When setup needs a choice (an install fallback, a retry, a missing tool), pick the safe option, say which in your next report, and keep going: never stop to ask about it. Ask only for product decisions.
- **Ask instead of guessing** when a choice changes the ticket's outcome: `armada ask "<question and your recommendation>" --options "<a> | <b>"`. Your phase becomes `blocked` and the question reaches the coordinator's inbox. Then **stop and end your turn**: the answer arrives as a message in this session, not in a command's output. When it arrives, report the phase you resume, for example `armada report implementing --message "resumed: <the decision>"`. Decide reversible technical choices yourself and record each one, with its reason, on the ticket and in the pull request.
- **Show the owner when your brief says so.** A brief with an "Owner validation" block names what the owner must see before the work goes on (a design ticket: the mockup itself). Ask one question judged in about a minute: a one-line headline, at most three checks and a sample of at most five items (default at most four images, text excerpts at most 40 lines). Never ask the owner to read a diff. Keep longer context folded with `--details-file`. Produce it, then `armada validate "Does the card read clearly?" --check "The title is legible" --check "The action fits on a phone" --attach card.png --excerpt output.txt:10-40 --details-file context.txt`: the attachments and the question go to the owner's Validations page on Armada, your phase becomes `awaiting-validation`, and the command prints the approval link. Then **stop and end your turn**: the coordinator relays the owner's decision in this session. On "Request changes", revise and run `armada validate` again (it replaces the open one); on approval, report the phase you resume, or, for a design ticket, stop: the coordinator closes it and building it is another ticket. Never merge or build what the owner has not approved.
- **The ticket is the source of truth.** Read it, its parent spec and the hand-back comments of its merged blockers in full before planning.
- Work only in your own branch and worktree. Never touch another agent's checkout, and stop only the processes you started.
- Reserve shared numbers and names with `armada reserve`, never guess. Use `armada reserve <key> --next --floor <last used number>` for numbers, `--value <name>` for names, or a key alone for exclusive resources. `armada reserve --list` shows the holders. Reservations end on release and remain used after merge; `armada unreserve <key>` frees your ticket's open reservations early. If Armada is unavailable, ask the coordinator before choosing a value. After a lost response, list before retrying.
- Never print, commit or log a secret.
- For every visible change, capture screenshots under a gitignored directory, then `armada attach <ticket> <files|https-urls>... --caption "<what to check>"`. Link the returned private dashboard URLs in the pull request description. Never commit screenshots to show a change. PNG, JPEG, WebP and GIF images are limited to 2 MB each; only the project's organization members may open them. `--for <item>` associates evidence with an owner's validation reference when one exists.
- **The project's secrets** (an LLM provider key, a test database URL) come from Armada, never from your launch environment; `armada secrets` lists their names. Use them, in this order: `armada run -- <command>` for tests, builds and dev servers (they go in that command's environment only); `armada secrets export --file <path>` for a tool that reads a dotenv file, at a path git ignores (e.g. `.env.local`). Never run `armada secrets get`, and never echo, `env` or `printenv` a value: your command output is your transcript. `armada run` masks non-interactive stdout and stderr, including split output chunks; `--redact` forces masked pipes when stdout is a TTY (otherwise interactive output is unmasked, with a warning). Messages and Linear comments are masked too. Values under eight characters and transformed or encoded values are not protected: masking is a safety net, never permission to print or paste a secret. A secret you need and do not have: ask the coordinator for it by name.

## Steps

1. **Claim** with the exact commands your brief starts with, for example `armada claim <ticket> --runtime conductor --handle "$CONDUCTOR_WORKSPACE_ID/$CONDUCTOR_SESSION_ID"`. Install the Armada version the brief names first; if it gives a fallback command, use it wherever this skill says `armada`. If neither installs (a version npm does not serve yet), install the newest published one (`npm install -g @the-vibe-company/armada`), say so in your first report, and go on. When the brief has an `armada login --launch-token <token>` line, run it once, after installing Armada and reading this skill, before the claim: it signs your workspace in to Armada for your ticket only, and Armada then gives your `claim`, `report`, `ask` and `release` their keys, so none is needed in your environment (do not ask for one; `armada whoami` shows the sign-in). The token works once, within the hour; never copy it anywhere else. If it is refused, or a later command says you were cut off from Armada, stop and say so in your reply: the coordinator decides whether you get a new one. A token shown as `armada_launch_••••` is the masked one of the brief's human view: it signs nobody in, and `armada login` says so; ask for the `armada brief <ticket> --prompt` text. The claim assigns the ticket, moves it to In Progress, sets `Agent phase = planning` and your `Agent runtime`, and posts the `Agent claim` comment. If it refuses because another claim exists, stop: the older claim wins.
2. **Branch.** Use the branch named after the ticket (the tracker suggests one, for example `feature/abc-12-short-title`), created from the latest default branch.
3. **Plan.** Declare the relative paths or globs you intend to change with repeatable `--paths "packages/core/src/file.ts,skills/**"` on your plan report (at most 50 paths, 200 characters each, no `..`). Read the overlap warnings and tell the coordinator before touching another worker's files; glob/glob matches mean they may overlap. Write the plan: what changes, how it is tested, and the checks a person could observe when it is done. Your brief's "Plan" section says in one line whether it needs approval (from `[policy] plans` in `armada.toml`, or a label on the ticket); follow that line, do not guess. Pre-approved: post the plan with `armada report implementing --plan-file -` (or `--plan-file <path>`) and go on; do not enter `awaiting-approval`. Otherwise post it with `armada report awaiting-approval --plan-file -`: it creates a `plan` item in the coordinator's inbox. `--plan-file` posts the plan as its own block, under a one-line status (`--message` sets that line, else the plan's first line). Push your branch and wait for the coordinator's decision in your session. On approval, report `implementing`; on amendments, report `planning`, revise the plan and submit it for approval again.
4. **Implement** test-first. A material change to the approved plan needs a new approval.
5. **Ship.** When CI is red, start with `armada ci why <pr>`. Use `armada ci why <pr> --rerun` only for a declared `[[ci.known_failure]]` or a runner problem: every failing check in that workflow run must qualify, and GitHub must report attempt 1 on a completed run. It reruns failed jobs once and names each known flake's root-cause ticket; mention those tickets in your next report. Unknown or external failures, incomplete evidence and attempt 2 or later are refused. Fix the underlying failure after a second failure; there is no force override. An uncertain rerun outcome must be inspected on GitHub before any further action. Fix an unknown failure; do not call it flaky without a project rule. Use `--sha <sha>` or `--branch <branch>` for a commit or branch instead. `armada report shipping --pr <number> --message "Preparing the pull request for independent review"`. Use the bundled `ship-pr-dev` skill by default, including its independent `review-code-dev` gate and report-only `capture-learning-tools` pass. At the independent `review-code-dev` review gate, report `armada report shipping --stage review --pr <number> --message "Independent code review started"` (omit `--pr` if no PR is open yet). Once that review passes, report `armada report shipping --stage ci --pr <number> --message "Independent review passed; checking CI"`. Report `review` again when changes need another independent review, and `ci` after it passes. Keep `--stage review|ci` on repeated shipping reports so the current step stays explicit. These stages are Armada data, not Linear labels; other phases do not take `--stage`. Within that workflow you own delivery (Git and the PR); its delegated helpers are its workers. The Armada coordinator still owns merging. If it cannot run (for example the OCR download or isolated reviewer is unavailable), record the exact limitation and use the fallback: run the repository's local checks, open the pull request with a Commitizen title (`feat(scope): …`), link it on the ticket, and fix CI until every required check is green.
6. **Bring the default branch in** right before hand-back (rebase, or merge it into your branch; squash merges make both fine), and get CI green on that final head. If the brief has "Live acceptance", commit and push a clean checkout, then run `armada acceptance run` (or `--name <name>` for one check) at that PR head. Fix every error the command prints within this ticket. A new head needs a new pass. Each check has a timeout and a per-ticket run cap; failed, timed-out and interrupted attempts count. At the cap, ask the coordinator to grant more with `armada acceptance allow <ticket> --runs <n> --reason "<why>"`. Commands needing secrets use `armada run -- …`. Linear records the evidence even when Armada is unavailable. Never force-push a branch someone else pushed to.
7. **Hand back.** Fix or reply to every review thread (including cubic), then resolve every thread before handing back. `armada report ready-to-merge --pr <number> --sha <full 40-character head SHA> --shipped-with "ship-pr-dev"`. For the fallback, use `--shipped-with "fallback: <exact reason ship-pr-dev could not run>"`. The generated hand-back line names the shipping path in Linear and `armada inbox`. Armada also refuses a hand-back until every applicable `[[acceptance]]` check has a Linear pass on that exact head (declared paths matched against PR files; an incomplete file reading or a rename with no original path applies every rule). Armada refuses a short SHA, a SHA that is not the pull request head, a red check, or unresolved review threads. If the review-thread reading is unavailable, Armada warns; check and resolve them yourself before handing back. Then report to the coordinator: `shipped with ship-pr-dev` or `shipped with the fallback: <reason>`, pull request URL, full SHA, CI state, the decisions you made, and what the next tickets need to know.

If you stop without finishing, run `armada release --reason "<why>"` so the ticket is free again.

## When a command is missing

This skill is versioned with Armada; an older CLI may lack a command (`armada --help` lists them). Do the same step by hand in the tracker, keeping the protocol: exactly one label from the phase group (`planning`, `awaiting-approval`, `implementing`, `shipping`, `blocked`, `ready-to-merge`, `awaiting-validation`) and one from the runtime group; a first comment `Agent claim — runtime: <runtime> · session: <id> · branch: <branch> · started: <ISO date>`; and every comment starting with `Agent status: <phase> — <one-line summary>`.
