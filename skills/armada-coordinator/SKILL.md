---
name: armada-coordinator
description: Coordinating an Armada fleet of coding agents on one project. Use when designated coordinator, or asked to launch workers on ready tickets, answer their questions, merge their green pull requests, or resume a fleet in a new local or cloud session. Reads the fleet with armada status and armada inbox and drives workers through the runtime guide skill.
---

The coordinator turns the owner's intent into merged pull requests. Each worker owns one ticket; the coordinator picks what runs, answers questions, merges and reports. There is one coordinator per project. `armada.toml` names the program root, the label groups and the policy; the `armada-worker` skill is what every worker follows.

**Standing authority.** Unless the owner said otherwise, they delegate reversible technical decisions, plan approval and merging to you: act, then report. Escalate only product decisions, irreversible or outward-facing actions, and anything that spends money.

**Use the worker's runtime interface.** Herdr and Conductor workers use integrated commands; Claude Code subagents use the `armada-runtime-claude-code` guide. `armada status` and `armada inbox` read both persistent runtimes' live state. `armada stop <ticket>` archives a Conductor workspace after release or merge and safely removes a clean, pushed herdr worktree. Use `armada launch <ticket> --runtime conductor|herdr` for persistent workers. `armada answer` delivers answers and notes to both persistent runtimes. Use the matching guide when a runtime operation reports a limitation.

## Take over a run

A coordinator may start cold, on a laptop or in a fresh cloud session, with nothing but the repository and a sign-in to Armada. Everything it needs is in the tracker, GitHub and Armada; the Armada [runbook](https://github.com/The-Vibe-Company/armada/blob/main/docs/runbook.md) says how to start one.

1. **Sign in to Armada.** `armada doctor` (or `armada whoami`) says whether this terminal is signed in and to which organization. If not: a person runs `armada login` and approves the code in the browser; a headless coordinator (a cloud workspace, CI) sets `ARMADA_API_KEY` to an organization API key an owner created on the Organization page. Signed in, Armada gives your commands the organization's keys, and every brief carries a one-time launch token, so no worker needs a key in its environment. Keys set in the environment still win over Armada's: they are the override for CI and a self-hosted Armada without accounts.
   The secrets workers need to build and test (an LLM provider key, a test database URL) are kept per project in Armada: `armada secrets set <NAME>` (owner or admin; `--org` for every project) reads the value from a hidden prompt, `--value-stdin`, or `--from-env <VAR>`, which moves a variable you already have without you ever reading it. Never put a value on a command line or in a brief; `armada secrets` lists the names, and `armada doctor` names those `[secrets] names` in `armada.toml` expects and Armada lacks. Workers fetch them with `armada run`; a worker of another project never gets them.
2. **Find your coordination ticket.** When the owner gives the coordinator a ticket of its own (a run to carry out, for example "run this ticket end to end"), that ticket holds the run's history. Read its comments, newest first. A last comment `Agent status: released — <text>` is a hand-over: the previous coordinator stopped on purpose, `<text>` is the state it left (who runs, what was asked and answered, what remains), and the ticket is back without agent labels, waiting for you.
3. **Claim it with your own handle**, never the previous coordinator's: `armada claim <ticket> --runtime <your runtime> --handle <your handle> --branch <default branch>`. In a Conductor workspace the runtime is `conductor` and the handle `"$CONDUCTOR_WORKSPACE_ID/$CONDUCTOR_SESSION_ID"`; on a laptop, the runtime you run in (a value of the runtime label group, for example `claude-code`) and a handle that names your session. The claim is refused while the previous coordinator still holds the ticket: ask the owner whether it stopped before releasing it for them. Without a coordination ticket, skip this step.
4. **Read the fleet** (step 1 of the loop): `armada status` and `armada inbox` give each worker's handle, phase, question and hand-back. Trust them over the hand-over comment where they disagree: the comment is older. If a worker is in flight, start `armada watch` in the background now (see [Keep watching](#keep-watching)).
5. **Report on your ticket** as a worker would, `armada report implementing --ticket <ticket> --message "<what you found and do next>"`, at least every `policy.silence_minutes`, and post the run's evidence there when it ends.
6. **Hand over** when you stop before the run ends: `armada release --ticket <ticket> --reason "<state so far and what remains>"`. It posts the `released` comment the next coordinator reads. Write it for a reader with none of your context.

## Loop

1. **Read the fleet** with `armada status` and `armada inbox`, never from memory. Done when you can name every ticket in flight and its phase, every ready ticket, every pull request waiting, every silent worker and every pending question, plan or request.
2. **Answer what waits for you first.** For each question in `armada inbox`: decide it, or escalate it to the owner when it is a product decision: `armada ask-owner <ticket> "<question>" --choices "<a> | <b>"` puts it on the owner's Validations page and prints the link to send them; their pick arrives as a `decision` item. For each `plan` item: read the full plan, approve it or give concrete amendments. For herdr and Conductor, deliver and record the decision with `armada answer <item> "approved"` or `armada answer <item> "<amendments and reason>"`. The worker resumes with `implementing` on approval, or returns to `planning` and submits a revised plan. `armada answer` delivers herdr and Conductor answers automatically. For Claude Code, deliver the decision in the worker's session with the runtime guide's *message* section first, then record it. Decide reversible choices yourself and prefer the option that keeps behaviour observable. When two workers need the same shared resource (a migration slot, a generated file, a version number), set the rule once and tell both. A message the worker did not ask for (main moved, bring it in) is delivered and recorded with `armada answer --note <ticket> "<message>"`. A live herdr `runtime-blocked` entry has no item id: read the pane and answer by ticket. Done when the inbox shows no open question or plan.
3. **Carry out the owner's dashboard requests.** They are the owner's word, signed with their name; they never reached a worker.
   - `answer-request` (it names the question or plan it answers, `answers #<id>`): run `armada answer <request id> "<the owner's answer or plan approval>"`; herdr and Conductor receive it automatically. For Claude Code, deliver with its runtime guide first. That resolves the request and its question or plan, and the ticket names who answered. If the item is gone (the worker was released or changed phase), `armada answer <request id> "<why>"` closes it.
   - `launch-request`: launch the ticket as in step 5. A request may name a label-routed profile or one the owner chose; otherwise choose from the profiles' `when` rules. Pass `--profile` and `--reason` when a choice or override is needed. The worker's `armada claim` resolves the request and posts who asked. If the ticket must not start (it collides with work in flight, or its plan changed), decline it: `armada answer <request id> "<why>"`, and tell the owner in your report.
   - `decision` (THE-885): the owner decided something you or a worker sent to their Validations page. A merge they approved: `armada merge <pr>`. Changes requested: deliver them in the worker's session with the runtime guide. A validation approved: tell the worker; for a design ticket, `armada done <ticket>` records the design on the ticket and closes it, then cut the ticket that builds it, blocked by this one. A choice to a question you escalated: deliver it as the answer. Then `armada answer <item> "<what you did>"`.
   Done when the inbox shows no open request.
4. **Check stopped or silent workers and workers that never started** with the runtime guide's *status* section. Armada checks Conductor itself: `stopped` means its session is idle in an active phase and it did not hand back; read its last reply and message it to resume, or release and relaunch it. Fresh working sessions only raise silence past twice `policy.silence_minutes`, with the observation named in the alert; archived workspaces end their claims. A worker that is still working gets a nudge to report; a worker that died is relaunched or its ticket released. A `not-started` entry is a worker launched that has not claimed after `[policy] not_started_minutes` (10 by default); it says whether the worker never used its launch token (it never reached its `armada login` line: an install that failed, a prompt cut short) or signed in and stopped before its claim. Read its session: a worker stuck on a setup choice gets a message to take the safe option and go on; one that is gone is launched again with a new brief, or its launch revoked on the dashboard's Workers page. The entry clears on the claim.
5. **Launch ready tickets** that do not collide with work in flight, one at a time:
   - pick the ticket from the frontier in `armada status`;
   - run `armada brief <ticket>` and resolve its warnings. A matching `[[conductor.routing]]` label rule wins. Otherwise, when profiles have `when` rules, the brief prints **Choose a profile** and mints no launch token. Read the ticket and its parent spec; match each profile's plain-language rule and prefer the one covering most files the ticket will change. If it spans front end and back end, choose where most of the work is and say so. Run `armada brief <ticket> --profile <name> --reason "<why>"`, naming the files or work that justify the choice. Armada never calls a model to classify tickets. Only projects without `when` rules fall back to `default_profile` (or their only profile). Override a matching label rule only when the labels mislead, with the same reasoned command. Keep `--profile` and `--reason` on every subsequent `--prompt` call; the reason reaches the worker's claim, status and agent page;
   - judge `[[policy.validation]]` when `armada.toml` has rules, the same way: each says in plain words which kind of ticket the owner must see first (`when`) and what the worker shows (`then`). Most tickets are none: `armada brief <ticket> --validation none` (no reason needed). When one applies (a design ticket, a new screen's look), `--validation <n> --validation-reason "<why this ticket is one>"`: the prompt then tells the worker to submit its work with `armada validate` and stop, and the claim records your judgement. The brief refuses until you judge, and prints the command to copy;
   - pre-approve a plan with `--pre-approve --reason "<why>"` on `armada brief --prompt` or `armada launch`, never in notes. It adds the project's plan-approved label, so the brief tells the worker to post its plan as `implementing` and go on; relaunches keep the label. Remove the project's needs-approval label first if Armada refuses. Preview briefs and dry runs only say what would change;
   - launch Conductor or herdr with `armada launch <ticket> --runtime conductor|herdr`, keeping the chosen `--profile`, `--reason` and validation flags. Runtime may be omitted when the profile settles it. Use `--notes <file|->` for the boundary with parallel workers or decisions not yet on the ticket; notes are context and do not pre-approve a plan. `--dry-run` checks settings and preflight without creating anything. Native launch needs an Armada sign-in, carries the one-time token through stdin, protects against duplicate launches and prints the worker’s handle/link;
   - for a Claude Code profile, use `armada brief <ticket> --prompt` and launch through the Agent tool as `armada-runtime-claude-code` says. Human and `--json` brief previews mint nothing. Keep the profile, reason and validation flags on the prompt call. Put conventions every worker needs in `[brief] extra`;
   - check the claim: `armada status` shows the ticket in flight, phase `planning`, with the handle the runtime returned. Done when every launched ticket is In Progress with a claim.
6. **Merge handed-back pull requests** one at a time with `armada merge <pr>`. An open `hold` pauses merges for every coordinator: inspect it with `armada hold`, merge a fix with `--through-hold "<why>"`, then verify recovery and resume with `armada hold clear <id> --reason "<what was verified>"`. Do not clear a hold just to let the fix merge. When `armada.toml` has `[policy] merge_approval`, judge each pull request against it in plain words: look at its files and what users will see. When it may merge on its own, `armada merge <pr> --reason "<why>"` (for example "CLI only"); when the rule keeps it for the owner, `armada merge <pr> --ask-owner --reason "<why>"` (for example "touches components/timeline"): it merges nothing, posts the approval link on the ticket and prints it; send it to the owner, and merge once their approval arrives in your inbox. A new head needs a new approval. Either way the merge records how it was decided. Without the rule, merge on your own (`--wait` when main moved since the hand-back, `--no-ticket` for a pull request no ticket owns), following [MERGE.md](MERGE.md). `armada merge` archives the merged worker after GitHub confirms the merge; never archive before it prints "Merged". Use `--no-archive` to retain it, or the printed `armada stop <ticket>` command when cleanup fails. Done when the pull request is merged, the ticket is Done with its agent labels removed, and every in-flight worker affected by what landed has been told. When the repository's rules (`AGENTS.md`) ask you to ship each merge through its release pull request (release-please's `chore(main): release …`), merge that one next, as "The release pull request" in [MERGE.md](MERGE.md) describes.
7. **Turn findings into tickets.** A gap a worker reports or a bug you see becomes a ticket under the right spec, with blocked-by relations, and is launched when ready. No finding lives only in a transcript.
8. **Report to the owner** in their language (`tracker.language` in `armada.toml`, or the owner's personal setting): what merged, what runs, what you decided for them, and the one thing they must do, with its exact place (a URL, a setting). Outcomes and numbers, no process narration.

Repeat from step 1.

When the owner asks where things stand, run `armada digest` and paste its text; do not write the status by hand. Use `--since 4h` for an explicit window or `--send` to post the same project summary through its configured channel. Owner-facing text follows `[tracker] language`, with `--lang en|fr` as an override.

## Cut and repair specs

Specs are direct children of the configured program root. Armada reads both `Spec N — Name` and the legacy `Spec N/M — Name`; use `armada spec add "<name>"` to append one with the **In short** template and print its URL, then fill in the outcome, why, observable checks and dependencies before cutting its tickets.

The default `[tracker] spec_titles = "N"` leaves existing titles alone on append. Tell projects whose own rules require N/M to set `[tracker] spec_titles = "N/M"`: adding then previews changes to every total and needs `--apply`. Both forms remain readable regardless of that setting.

For a middle insertion, `armada spec add "<name>" --at 5` previews only; inspect the suffix renames, then repeat with `--apply`. In N mode, earlier titles stay untouched and shifted legacy titles keep their denominator. `armada spec renumber` previews a stable repair of gaps, duplicates and stale totals; `--apply` normalizes all titles to the configured style. Writes are sequential and stop on failure with the unconfirmed operations listed. Inspect Linear before retrying a failed write, which may have arrived, and preview a repair as needed. These commands refuse worker sessions.

## Keep watching

You only learn of something new when a command you run ends. So while a worker is in flight, always have exactly one `armada watch` running, in the background (in Claude Code, a Bash command with `run_in_background`; in another runtime, its own way of running a command in the background). It waits until something needs you (a question, a plan, a request, a hand-back, a merge hold, a silent worker or one that never started, you have not been shown yet), prints it and exits, and you are woken. Armada being down does not end it; a harness time limit may kill it, and it tells the dashboard you are at work.


Use `armada watch --follow` only where every output line reaches you: a terminal, a herdr pane, or a harness tool that turns each background output line into a notification (for example Claude Code's Monitor tool, where available). It prints each question, plan, hand-back, request or worker alarm and keeps running; a printed line is marked seen even if the harness did not read it. Harnesses that wake only when a command ends must keep plain `armada watch`.

- Set `--for` below the harness's command limit: `armada watch --follow --for 50` ends cleanly after 50 minutes and prints `resume: armada watch --follow ...`. Plain `armada watch --for 50` is bounded too.
- Restarted follow resumes this machine's stored cursor and seen entries. `--since <cursor>` on another machine reads events after that cursor and shows every open inbox entry once, marked `open`. Follow keeps polling while idle (every 60 s; every 15 s with workers in flight); requests are short and unchanged reads answer 304.
- `--tickets ABC-1,ABC-2` and `--kinds question,hand-back` filter lines. Informational events are opt-in: `--kinds claim,report,release,merge,handover` or `--kinds all`; `handover` is a report entering ready-to-merge. `--json` prints NDJSON with a cursor on every line. `--mine` is refused until "Show each coordinator only its own work" lands; `--all` uses the current whole-project scope.
- Follow and plain watch share one lock per project on this machine. `armada watch --stop` stops either; the stop hook accepts either as a running watch.

- From any folder, set `ARMADA_CONFIG=/path/to/armada.toml` or pass `--project <slug>` to use this machine’s last watched checkout; `--config <path>` overrides both.
- `armada inbox` and `armada status` run fine while a watch runs: never stop it to read the inbox or the fleet. To stop this project's watch, use `armada watch --stop`, never `pkill` or `killall` patterns: those can kill other projects' watches on the same machine.
- Start it as soon as a worker is in flight, and start it again right after acting on what it returned. Never end your turn with a worker in flight and no watch running: that is how a hand-back sits unmerged.
- The last line of `armada inbox`, `armada watch`, `armada merge` and `armada brief` says whether to: `2 workers in flight (ABC-1, ABC-2) — keep watching: armada watch`, `armada watch is already running (pid …)`, or `nothing to watch`. Follow it. A second `armada watch` on the same project only says the first one is running.
- `armada watch` exits with "nothing to watch" when no worker is in flight and nothing is open: the round is over.
- Ordinary releases leave the watch running. `armada status` and `armada inbox` print one quiet release notice per 24 hours on this machine, across versions; the dashboard's coordinator card shows that an update is available. A `version` item means the server requires a newer CLI or this project's installed pointer descriptions/vendored skills differ. Both watch modes stop on required upgrades, even when follow filters hide other kinds. Run `armada upgrade`: it waits at most five publication checks over about two minutes, installs the exact npm release, verifies `armada --version`, and uses the upgraded doctor to judge setup. Only outdated setup runs `armada init --merge`, through the normal setup-only merge checks. Tell workers in flight nothing: each keeps the version its brief pinned unless the release notes say otherwise.
- Your own coordination ticket is not a worker: the watch and the re-arm line leave out the claim whose handle is yours, taken from `ARMADA_COORDINATOR_HANDLE`, else from Conductor's workspace and session. Outside Conductor, set `ARMADA_COORDINATOR_HANDLE` to the handle you claimed with.
- In Claude Code, the stop hook `armada init` installs refuses to end your turn while workers are in flight and no watch runs, and tells you to start one. It holds only the checkout where `armada watch` ran, never a worker. If it misbehaves, `ARMADA_STOP_HOOK=off` in the environment turns it off; say so in your report. Other runtimes have no hook: follow the same rule yourself.
- A runtime that cannot run a command in the background uses `armada inbox --wait` instead, again and again: it returns when a new item arrives or at its timeout (default 300 s, `--timeout <seconds>`; keep it under your command time limit).

## Rules of thumb

- Never pipe Armada commands through `grep -v`, `tail` or `head`: the last lines say whether a merge happened and what to do next.

- When asking the owner to validate a design or change, attach what they must see with `armada attach <ticket> <files|https-urls>... --caption "<what to check>" [--for <item>]` and include the returned private dashboard URLs in the request. Keep screenshots out of git. Only organization members can open the evidence; each image is at most 2 MB.

- Merge only after the worker's hand-back; a green pull request can still get one more push that brings the default branch in.
- Parallel workers in one area collide: stagger them, or give each a disjoint area and tell them the boundary.
- Everything that must survive your session goes to the tracker or the repository. The next coordinator may be a fresh cloud session with none of your context: it resumes from `armada status` and `armada inbox`.
- When a command named here is missing from your Armada version (`armada --help`), do the step by hand with the same protocol and say so in your report.
