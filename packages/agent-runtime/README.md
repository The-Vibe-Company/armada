# Sandbox runner (protocol 1)

Owned by #510–512; no provider/server/SQL-registry integration is included.

## Distribution and boot

`bun install --frozen-lockfile` with Bun 1.4.2, then
`cd packages/agent-runtime && bun run build` on the target Linux architecture.
`dist/` contains `main.js`, native `claude` 2.1.319, native `codex` 0.167.0,
and a version manifest. Codex retains its complete native resource tree
(`codex-runtime/`, including code-mode host, bubblewrap and ripgrep); `codex`
is an internal symlink to that tree. Add `dist/codex-runtime/codex-path` to
the Codex environment PATH. The SDK is 0.3.319. The JS bundle has no unpublished
workspace imports. Install Bun 1.4.2 separately. Start `bun main.js` with
bootstrap JSON on a private stdin pipe, closing it after the document; detach
with the placement supervisor. Never pass credentials as arguments.

Bootstrap fields: `root` (private durable directory), `cwd`, `port`, `grant`,
`claudeExecutable`, `codexExecutable`, `claudeEnv`, `codexEnv`, `ingestUrl`;
optional `codexAuthJson` and `mcp`. Each environment is an explicit allowlist,
not an inherited process environment. Caller must include required PATH/HOME
and only the selected harness credential. Provider management/user/database
credentials must never be supplied. `root/claude` and `root/codex` hold native
session state; `root/journal.sqlite` holds the local WAL ledger. Fresh bootstrap
reinjects transient auth after restore. Checkpoint rebuilds an allowlisted sanitized session tree and removes complete
live harness homes after closing drivers; model session files remain.

Goldens must contain only the distribution, not `root`, launch bootstrap,
SSH host private keys, or model session/config directories. Snapshotting arbitrary
user home directories is NOT a secure golden builder. Placement owns that rule.

## HTTP

POST JSON to the runner. Every request carries `version:1`, `requestId`,
`sandboxId`, and the discriminated `op` in exported `RunnerRequest`. Responses
are `{version:1,requestId,result}`; refusals use an `error` field.
Requests require `x-armada-runner-grant` matching the in-memory, expiring,
sandbox/generation-bound `Grant`. Use this header in addition to Modal's
connect-token Authorization header (Modal strips the latter). Rotate on every
physical generation and retire old tunnels. Never reuse a grant on restore.

Operations: health, prompt, getPrompt, steer, interrupt, events, exec,
getExec (detached exit evidence), checkpoint. Prompt input and exec input use
core Provider request shapes. Steer requires a conversation ID; interrupt without
one targets all active conversations. Events use opaque decimal local sequence
cursors, oldest first. They are not the later server registry's SQL cursors.
Mutating request IDs fence side effects: an interrupted request can report
`request_outcome_unknown`; do not blindly retry with a new ID.

`IngestClient.append` is the narrow #513 integration seam: sandbox, generation,
producer sequence and event. Server must durably deduplicate and commit before
returning its highest contiguous `acknowledgedSequence`. Checkpoint refuses
until all local events are acknowledged, interrupts active turns, drains exec,
closes harnesses and checkpoints WAL. It leaves admission closed: snapshot/stop
then start a fresh runner. An unavailable ingest service must block checkpoint,
not silently drop acknowledged history.

`McpConfiguration` is optional, transient `{revision,servers}` with typed HTTP
URL/headers and local stdio command/args/env. Both drivers apply this at first
start/resume. Use authenticated `configureMcp` to replace revisions for future turns; active
turns keep their existing snapshots. No registry, OAuth broker, or refresh
ownership is implemented here.

## Checkpoint hardening and protocol-1 integration notes

HTTP request/receipt shapes are unchanged. New explicit checkpoint refusals:
`checkpoint_exec_processes_live` and `checkpoint_exec_identity_unverifiable`.
A refused barrier keeps admission closed and can be retried after quiescence.
Exec records carry boot ID, process-group ID and Linux start-time identity.
On runner restart a matching live group becomes `running_after_restart`; a
lost/unverifiable outcome remains `unknown_after_restart`. No persisted PID is
signalled during restart. Final exit codes are returned only when the actual
child's close event supplied them. A shell exit does not itself prove that
its entire background process group is gone.

Harness subprocesses own separate process groups. Cleanup waits for actual
child exit and group quiescence, with bounded force-kill fallback; failure
refuses checkpoint rather than claiming that streams closing stopped writers.
Codex uses the official `account/login/start` API-key flow over private stdin
when a selected key is supplied. Native auth-file credentials remain supported
without opening/reading those files in the runner.

`HarnessState` now persists only allowlisted native transcripts:
Claude `projects/**/*.jsonl` and project tool-result text; Codex
`sessions/**/*.jsonl` and `archived_sessions/**/*.jsonl`. Everything else in
runtime-owned harness homes is transient, including refreshed credentials,
config, logs, MCP caches and indexes. Checkpoint sanitizes transcript content,
replaces the saved session tree, and removes whole live homes. Restore rebuilds
native session directories and requires fresh bootstrap auth/MCP config.
`main.ts` isolates HOME and XDG directories under each live harness home;
Codex credential stores are forced to files there. If Git tooling needs a
separate per-launch configuration, supply its explicitly scoped environment
(e.g. GIT_CONFIG_GLOBAL) instead of relying on the original user's HOME.

`createRedactor` applies to output, events and saved transcripts; `Journal.sanitize`
rewrites old persisted bodies and vacuums/checkpoints SQLite with secure deletion.
No native auth/cache files are read to discover refreshed secrets. Exclusion of
those stores, not a two-filename blacklist, is the security boundary. These
controls cover runner-owned native state; they cannot prove arbitrary user
workspace files or deliberately escaped processes contain no secrets. Golden
creation must install only the clean code distribution, never a launch root or
user home. The build deletes its previous output before copying pinned code and
native dependencies, so stale launch files cannot ride along in a rebuild.

The optional MCP seam remains server-owned; no OAuth broker or grant refresh
has been implemented. Authentication secrets must be supplied through private
bootstrap/env, never MCP command arguments. Configure fresh short-lived gateway
headers/env on restore. Session sanitization removes configured secret values
and structured credential/config fields, not conversation/session IDs.

Opt-in model smoke (not unit verify):
`bun packages/agent-runtime/scripts/codex-smoke.ts --run`.
It uses only the already selected harness environment, creates an isolated
system-temp root, never prints native messages or credentials, bounds the run
to 90 seconds, and cleans up child groups and temporary state. The optional
`--record-terminal` captures only sanitized failed terminal fields, never raw
provider messages, auth responses or environment values.

## Retry safety and review regressions

Checkpoint admission is durably fenced in SQLite per generation before any
barrier side effect. A same-generation process restart retains that fence and
must not rehydrate native homes or reinject credentials. A fresh generation
still requires a fresh valid grant; old checkpoint request IDs never bypass
fresh authorization or imply admission. Checkpoint retries revalidate process
quiescence, upstream acknowledgement and sealed session bytes, not a cached
HTTP receipt.

Each sanitized session tree now has a version-1 `.checkpoint.json` manifest
with generation and SHA-256 file fingerprints. Files and seal metadata are
flushed before publication. A retry with no live homes preserves a verified
seal instead of publishing an empty tree. Modified seals, missing unverified
homes, and interrupted ambiguous renames are explicit refusals. Restore merges
sanitized live transcripts through a separate staging directory and never
mutates an already verified saved tree in place. Model sessions survive a
lost-response retry and a later fresh-generation restore.

Ingest acknowledgements are untrusted JSON: only nonnegative finite safe
integers within the previously acknowledged/sent range can advance SQLite.
Malformed responses leave the durable watermark unchanged; old poisoned
metadata is refused explicitly rather than silently interpreted as a cursor.

`src/codex-schema/PROVENANCE.json` records pinned native 0.167.0 regeneration:
79 checked-in generated files compared, 31 initially byte-identical and 48
formatting-only differences reconciled, 79/79 now byte-identical. Type syntax
review found no type changes (property quoting, parentheses and type-only
import ordering differed). The package-local Biome override excludes only
these upstream generated TypeScript bytes from rewriting; handwritten code
and tests still undergo normal lint/format verification. No inventory test
or global Codex installation is used as provenance.

Claude opt-in entrypoint, for the coordinator's privately injected selected
OAuth environment:
`bun packages/agent-runtime/scripts/claude-smoke.ts --run`.
It uses pinned native Claude, Opus 5.5 / medium, no auth-file reads or auth
response logging, system-temp state and a 90-second work deadline plus bounded
cleanup. It checks remember/sanitized checkpoint retry/restore/recall,
parallel conversations, scoped interrupt and native steer. It has not been
run against authenticated Claude in this worker environment.

## Secret-bearing MCP transport

Claude SDK 0.3.319 serializes `mcpServers` options into native argv. The runner
therefore **does not pass that SDK option**. It supplies the official native
`--mcp-config` file input through `extraArgs`, retaining `strictMcpConfig` and
empty `settingSources`. `PrivateMcpFile` atomically creates a 0700 per-turn
directory and a 0600 exclusive, no-follow file under the runtime-owned private
home. On Linux, directory descriptors anchor creation, native file access and
unlinking; only `/proc/<runner-pid>/fd/<directory-fd>/mcp.json` enters argv.
Configured homes that are symlinks or writable by other users are refused.
Neither headers nor stdio environment values enter native argv or the native
harness's global environment. The native harness gives stdio env only to the
configured MCP child, as intended by that protocol.

Per-turn cleanup unlinks the file and removes its directory on success,
interruption or failure; driver shutdown also releases outstanding configs.
Checkpoint waits for that shutdown, and the transcript allowlist excludes all
such config directories, including leftovers from an unclean process exit.
Codex continues to receive MCP configuration exclusively through private
app-server `thread/start` / `thread/resume` JSONL, not `-c` argv values.

The owner-boundary regression runs the actual pinned Claude SDK with a local
child observing kernel argv, its environment, config bytes and live filesystem
modes. Synthetic sentinels demonstrated argv disclosure before the fix and
path-only transport plus file/directory removal after it. A separate JSONL
child boundary verifies the Codex transport. These are not authenticated
Claude model claims.

Both opt-in smoke scripts accept `--public-mcp` in addition to `--run`. This
requests an actual `microsoft_docs_search` tool call against Microsoft's
[public, auth-free Learn MCP service](https://learn.microsoft.com/en-us/training/support/mcp).
The Codex gpt-6.1-sol / medium run passed with a real successful tool result;
no OAuth broker, gateway grant or registry was needed. Claude's corresponding
flag is ready for the coordinator's selected OAuth environment. Tool payloads,
auth responses and credential values are never printed by the smoke scripts.

## Additive protocol 1: configureMcp (#523)

Authenticated request (the existing `x-armada-runner-grant` is still required):

```ts
{
  version: 1,
  requestId: string,
  sandboxId: string,
  op: "configureMcp",
  configuration: McpConfiguration
}
```

Success is `{version:1, requestId, result:{revision}}`. New exported types:
`ConfigureMcpRequest`, `ConfigureMcpResult`; existing `RunnerRequest` includes
this additive operation. `validateMcpConfiguration(unknown)` is exported for
strict boundary validation and returns a detached, deep-frozen configuration.
`createRedactor` now returns the callable `Redactor` with `register(values)`.
`Journal.registerSecrets` and its stable `Journal.redact` function are the
runtime's shared dynamic redaction boundary. Native session persistence must
use that same `journal.redact` function, as the production entrypoint does.

The grant must be current/unexpired and match the sandbox/generation; both
in-memory and durable checkpoint admission fences are checked before changes.
Same current revision and canonical content is idempotent; changed content for
that revision is `mcp_revision_conflict`. Reusing an older accepted revision
is `stale_mcp_revision`. Revisions are opaque identifiers, not sortable dates;
523 owns authoritative lease ordering. Empty `servers:{}` removes all future
connections, including when resuming a previous conversation. Active turns
retain their immutable old snapshots and private files. No active SDK query is
mutated by this operation.

Configure requests bypass the normal request-result cache, including when a
request ID is reused: authentication, admission and revision checks always run.
The payload, headers/env, native config and request body are never stored in
SQLite, events, cache entries or checkpoint manifests. Only generation-scoped
SHA-256 revision/content fingerprints and a hashed current pointer are durable,
so stale/conflicting retries remain detectable after restart without storing
plaintext configuration. The active configuration and credential redaction
values remain private in-memory state; 513/523 must reapply authoritative config
on resumed service preparation before starting prompts. New credential values
are registered before metadata writes, snapshot replacement or acknowledgement;
old values remain registered to scrub still-active turns and saved sessions.

Limits: 64 KiB serialized configuration, 32 servers, 128-character revision,
64-character server names, 4096-character HTTP(S) URLs (no URL credentials or
fragment), 64 headers/env entries per server with 8192-character values, 64
stdio args with 4096 characters each, and 1024-character commands. Unknown
fields, mixed HTTP/stdio variants, invalid names, header CR/LF, NUL and invalid
Unicode are rejected without echoing input. Revision history and the in-memory
secret registry are bounded; budget exhaustion refuses replacement rather than
forgetting earlier credentials or revision history. Credential values belong
in HTTP headers or purpose-bound stdio env, never command arguments.

Linux-native tests use narrow platform guards for `/proc`, process groups and
private config descriptors. Portable HTTP/WAL/revision/checkpoint tests still
run on macOS. The coordinator's separate authenticated Claude receipt confirms
Opus 5.5 / medium restore/recall, parallel conversations, scoped interrupt,
native steer and the real public MCP tool (11 partial events); this worker did
not obtain or inspect its OAuth token or auth files.

## Private native prompt cwd (#529 / provider 513)

`RuntimePromptRequest` extends core `PromptRequest` with optional `cwd?: string`.
Only the private protocol-1 `prompt.input` and `DriverContext.request` use that
extension; the public Provider/CLI prompt contract is unchanged. Provider 513
supplies its persisted, server-validated per-harness native directory on every
initial or resumed prompt. The existing outer sandbox/generation grant and
input sandbox-ID checks still apply.

A supplied cwd must name an existing directory, be normalized and absolute,
contain no NUL, and fit the path limit; refused input yields `invalid_cwd`
without echoing it. Each driver captures `request.cwd ?? configuredDefault`
once per turn. Claude uses it for both SDK query cwd and actual child cwd.
Codex uses it for the app-server child, `thread/start`, `thread/resume` and every
`turn/start`, including restart steering. No global process cwd is changed;
steer retains its active conversation's captured cwd. The nonsensitive path
can persist in the local prompt journal and native session metadata.

This is native working-directory selection, **not confinement**: the VM owner
already has RCE. Repository/golden visibility validation remains server-owned.
No Boat wrapper, input-only Codex cwd bridge, main owner/repo alias, UI
configured-directory choice, CLI, server or provider registry is replaced here.

Regression evidence uses real SDK/JSONL child processes that create relative
files in their kernel cwd and record received native thread/turn cwd values.
Default-only behavior failed all three new owner tests before repair; repaired
behavior passes parallel conversations, scoped steer, resume and default
fallback. Native tests are Linux-gated; HTTP validation and WAL metadata tests
remain portable.

Additional bounded real Codex proof (pinned 0.167.0, gpt-6.1-sol / medium):
actual native `commandExecution` of `pwd` returned the initial selected directory,
then the same persisted session resumed with a different selected directory and
native `pwd` returned that directory. The proof checked both native tool cwd
metadata and actual command output, not the model's text assertion. No source,
environment or credential files were requested; only a sanitized boolean receipt
was retained outside the repository.

## Logical sandbox + physical generation seal identity (Modal fork fix)

`CheckpointIdentity = Pick<Grant, "sandboxId" | "generation">` is exported.
`Journal.checkpointPending(identity)`, `checkpointFence(identity, phase)` and
`HarnessState.checkpoint(identity)` now take that pair, **never generation alone**.
The production boot path passes the full grant; normalization copies only the
two public identity fields, never its bearer. Local checkpoint and MCP revision
metadata keys use collision-safe hashes of the canonical pair. Native session
seal manifests are version 2, `{version:2, identity:{sandboxId,generation}, files}`.
The authenticated HTTP request/response shapes remain unchanged.

Same sandbox ID + same generation remains sealed and retryable across process
restart. A different sandbox ID may start at generation 1 from a clean, completed
golden seal without inheriting the builder's admission barrier. A new generation
of the same sandbox can restore its existing sanitized sessions. No fence is
unconditionally cleared. Old generation-only seals and version-1 manifests
lack a trustworthy logical owner and fail closed; rebuild those experimental
goldens rather than deleting their barriers to make an ordinary resume pass.

The journal records only the public current identity. Cross-ID boot requires
that source identity's checkpoint be `complete`, and refuses inherited prompt,
session-map or event history (`golden_runner_history_not_empty`). Production
`HarnessState.restore(identity)` also refuses cross-ID native transcript files
or residual live config homes. Same-ID generation changes preserve session
state. Thus a successful regular checkpoint is **not** a golden-data scrubber.

Provider 513 golden policy: reject model prompts on credential-free builders,
quiesce and acknowledge through checkpoint, then scrub/reset native session,
auth/config and model-history state under the lifecycle lease before publishing
an image. Retain the minimal scoped source identity/fence when resetting the
journal, and retain/recreate an empty version-2 session seal for that source
identity. Do not delete the ordinary lost-response fence or treat an incomplete
source snapshot as a golden. No new wire checkpoint mode is needed for this
fix; the distinction is enforced at the builder lifecycle/publication boundary.
Golden scrubbing must not race a live runner or other filesystem writers.

The owner-boundary regression checkpoints a source, copies the actual sealed
filesystem, boots a fresh ID/generation-1 grant, checks HTTP readiness and prompt
admission, reseals the clone, then reopens the source and proves it is still
blocked. It also checks source-quiescence denial, old-token refusal, native/model
history rejection, owner resume, legacy refusal and exact manifest identity.

## Private exec Git authentication (514 integration contract)

Private boot JSON may supply `execEnv?: ExecEnvironment` independently of
`claudeEnv` and `codexEnv`. The exact allowlist is `GH_TOKEN`, `GITHUB_TOKEN`,
`HOME`, `PATH`, `GIT_CONFIG_GLOBAL`, and `GIT_TERMINAL_PROMPT` (only `"0"`).
Unknown variables, model/provider/database keys, NUL, invalid token bytes and
non-normalized HOME/config paths are refused. Default exec still receives only
public PATH/HOME plus disabled terminal prompts; nothing is inherited wholesale.
Tokens are frozen in memory, registered with the shared redactor before exec,
never included in shell argv or request bodies, and never reconstructed from
SQLite or snapshots. Reissue them through private stdin bootstrap after restore.
Model environments do not inherit this exec map. Supplying a known model key or
the runner grant as a Git credential is rejected by the production entrypoint.

Exported: `ExecEnvironment`, `RunnerExecutionOptions`,
`validateExecEnvironment`. `Runner`'s seventh constructor argument is optional
`RunnerExecutionOptions`; existing HTTP `exec` requests and core `ExecRequest`
are unchanged and do not acquire an arbitrary env field. Production boot owns a
private `exec-transient/gh` config directory, removes old caches before fresh
injection and deletes that tree after quiescence at checkpoint. Credentials
must not be placed in Git config or written by setup commands; this is explicit
subprocess authentication, not confinement against the VM owner's RCE.

`credentialFreeBuilder:true` in private bootstrap refuses Git/model credentials,
model prompts and nonempty MCP connections. Provider 513 must set it for golden
builders and omit credential maps. A normal launched/resumed sandbox defaults
to false and receives only the user's freshly resolved selected Git credentials.

Actual core caller contract confirmed read-only in `core/launch.ts` and
`core/github.ts`: core merges `githubEnv(token)` into `Provider.fork.env`, then
calls `Provider.exec` with `gitSetupCommand(identity)`. That command stores only
`$GH_TOKEN` as a runtime credential-helper reference; Git reads GH_TOKEN when it
asks for a password. Therefore 513/514 must explicitly project the two GitHub
aliases from fork env into **bootstrap execEnv**, not into a per-exec request,
and must not forward model keys with that projection. If native agents also
need Git auth/global config, their separately selected model environments need
an explicit authorized Git mapping; no exec-to-model inheritance is performed.
The coordinator must confirm worker514's adapter wiring against this contract;
this worker cannot inspect or change the other sandbox's implementation.

## Unknown-owner recovery gate

An absent `runner:identity` is allowed only when all runner tables/metadata are
pristine. Prompt/session/event/request/process history or any metadata cannot
be adopted by an incoming identity. Every legacy checkpoint key is checked,
not merely the incoming generation. `Journal.assertRestoreSource(identity)`
returns the verified prior identity (or undefined only for a pristine store).
Production boot passes that result into
`HarnessState.restore(identity, verifiedSource)` before binding the new actor.
Native files without a manifest or verified owner are likewise refused using
metadata-only traversal; auth files are not read to discover credentials.
Known same-ID ownership can recover unsealed native files after an unclean
restart. Clean scoped forks and ordinary same-ID retry fences remain intact.
