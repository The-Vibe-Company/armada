# PR-scoped hand-backs

This contract implements the existing 60fd second-hand-back mandate. It does not authorize a second worker, a new ticket scope, a merge, or a production rollout. The source and migration alone are not evidence of a deployed capability.

## Identity and observations

`hand-back/v2` identifies an immutable revision by project, registered repository, ticket, PR number, full original head SHA, and server-derived claim generation. Generation hashes the canonical runtime handle, claim timestamp and worker session ID. A released generation cannot report. Body, author and creation time never change; supersession and resolution are separate fields. Identical retries return the same ID; different evidence at an existing pin refuses.

A compatible worker reads its own state through the existing authenticated `GET session` (`ownHandBacks`); it receives no coordinator rights. The server checks the authenticated worker against the current claim before and after assembling the projection. A coordinator uses the existing `inbox/ticket` operation with the schema discriminator. Both return the actual configured server build revision, current generation, bounded open revisions and merge receipts. Unknown schema, missing revision, incomplete state or a foreign binding refuses. The list bound is 100; reaching it refuses admission rather than concealing work. This is a server observation, not a GitHub head attestation or atomic permission spanning subsequent writes.

The CLI negotiates before its first Linear ready report. Its existing fresh GitHub head/CI checks remain required. The store validates the URL/head/summary binding and current claim under the project lock, then commits the event and revision together. New heads compare and supersede only that PR's observed prior revision. An unscoped phase report preserves hand-backs; an explicit correction with the existing PR/SHA inputs resolves only the expected revision.

## Merge, queue and recovery

Selection uses that PR's current revision and its entire immutable status declaration, including continuation intent, reconciled with canonical Linear. A same-PR/same-SHA Linear rewrite left by a refused legacy writer is a disagreement, not permission to change the accepted intent. Explicit `--close` remains a separate deliberate choice. No latest-global comment, older matching head or unregistered fallback replaces this evidence. The ordinary gates, human phases, protections, lease and verified main-only integration remain in force. The queue stores the immutable reference while retaining FIFO, attempts, flags and reasons. A changed revision or a legacy queue row without its typed reference refuses without rewriting the entry.

Consumption records original and integrated heads separately. A verified main-only lineage belongs to that same PR. The transaction resolves only its selected revision and keeps an immutable idempotent merge receipt. Final closure refuses if a sibling remains. Partial merges retain ready-to-merge while siblings remain, otherwise implementing; newer human blocking phases are preserved. Continuation, archive and deferred launch are suppressed while siblings remain. ROOT decides the next action. Consumption is not a permit for later effects: phase writes and their confirmation re-read the confirmed receipt, generation and expected sibling references. A changed observation leaves cleanup pending. Continuation construction and native delivery revalidate too; a stale or unreadable scoped observation suppresses delivery and any manual-delivery instruction. Reads are not atomic with external writes: post-effect checks detect changes but cannot retract an already performed effect.

Repair treats unreadable scoped state as unknown and preserves the pending chore. The confirmed receipt controls partial versus final intent; a contradictory mutable chore refuses rather than downgrading a partial merge to Done. Inbox and overview queue status match the entire typed reference. A different queued revision is explicitly shown as stale and does not suppress the new hand-back notification; PR-only matching remains only for genuinely unbound legacy rows.

A lost response can retry the exact receipt. Historical partial receipts never reopen a released or replaced generation. A final receipt can finish Linear cleanup for its own released generation, but cannot act on a replacement claim. Generic completed-ticket snapshots cannot resolve typed revisions. No GET-to-GitHub atomicity is claimed; a sibling arriving during GitHub work causes cleanup refusal and visible pending work, not a fabricated final closure.

## Additive migration and legacy rollout

Migration 53 is reserved by the official Armada resource store: reservation 1117, `db-migration`, resource-only THE-812, owner lot60fd/CODE3a6e7822. It preserves migration52 and the old shared inbox index. Typed rows use internal `hand-back-v2`, projected as ordinary hand-back items with metadata. Added columns, per-PR uniqueness, receipts, queue reference and lease protocol are installed together. Historical legacy bodies/IDs are neither rewritten nor backfilled.

Existing simple legacy flows remain readable. An unresolved legacy hand-back prevents v2 admission. An active old merge/drain lease prevents the first v2 admission; project-lock serialization covers acquisition and renewal. Once a current claim uses v2, old writers and merge/queue operations refuse before their server effects, even after its last partial receipt. This cannot retrofit negotiation before a Linear write in an already-installed old binary, nor prevent arbitrary GitHub writes outside Armada. When a signed-in coordinator cannot read Armada, `--no-lock` cannot establish whether its ticket uses v2 and admission refuses. Compatible clients must be adopted before operational admission; no server-only rollout claim is sufficient.

Publication follows the maintained upstream PR, independent review and natural CI. The server's existing Vercel deployment and the weekday 07:00 UTC client release train are distinct. Record the effective server revision/schema and published client version/tarball digest before admission. Do not force a train, update other workers, run production SQL from a test workspace, or treat a local pack as a release. A rollback to an old server/client while v2 claims exist requires explicit owner recovery; it is not silently safe.

## Verification and evidence

The 26 SOURCE cases map to executable cases in `packages/dashboard/test/hand-backs.test.ts` (transaction, concurrency, immutable evidence, queue and legacy), `packages/core/test/merge.test.ts` (PR selection and human phases), `packages/core/test/worker.test.ts` (old server refusal before Linear writes), and `packages/cli/test/peek.test.ts` (two explicit hand-backs). Additional regressions cover claim replacement, final cleanup recovery, stale partial receipts, generic inbox reconciliation and authenticated own-session access. Tests use synthetic identities and isolated PGlite, never an AO worker identity. Passing fixtures does not establish server distribution or consumer admission.
