# Machine contract and lifecycle jobs

This is the Step 2a design for [#2750](https://github.com/The-Vibe-Company/armada/issues/2750). It describes the target after provider-run retirement. [Durable provider launch](durable-provider-launch.md) describes the earlier design and remains a reference for recovery cases.

## Why change the contract

In `packages/core/src/launch.ts`, `await launch.admit(...)` can allocate compute before `stores.sandboxes.insert(...)` records its owner. The durable provider launch design adds a request claim and deadline around that gap, but retains the golden operation fence and crosses the Modal source and child lifecycle leases. A worker that loses its claim can still have a provider operation in flight. The database then cannot infer whether the provider allocated, or whether a successor can safely retry, from claim expiry alone. Boat shares the provider admission boundary. Docker already journals host jobs and receipts, but its normal launch has a separate request worker and claim. Stop and resume also span sandbox claims and provider or host state. Steps #2755–#2766 replace those paths with a durable sandbox intent, a single runner claim and a provider reconciliation contract.

## Machine

Bind each adapter to the selected deployment and provider account or host. Every operation on a machine takes the Armada `(sandboxId, generation)`, including operations that need an additional physical ID. This pair identifies the incarnation and is also the basis of each operation's idempotency key. Replays of an operation use identical inputs. Return a definite conflict for a different intent on the same key. A restore carries the exact retained predecessor reference, while the new generation identifies the restore target.

| Operation | Contract |
| --- | --- |
| `create` | Allocate at most one machine for the generation from the admitted immutable image or snapshot, size and compute TTL. Return or recover the same physical identity across retries. |
| `bootstrap` | Install or re-establish the runtime for that incarnation. A replay converges on the same enrolment binding and one active runtime. Acknowledging a bootstrap does not publish readiness. |
| `stop({retain})` | Confirm physical exit. When retention is requested, first prove that the checkpoint or workspace belongs to the generation and persist its reference before destroying source compute. Replay returns the same retained result. Refuse unsupported retention before dispatch. |
| `resume` | Restore the exact retained predecessor into the target generation. Replay adopts the same restore instead of allocating again. Keep the predecessor recoverable until the replacement outcome is durable. |
| `delete` | Delete only the addressed generation and the explicitly scoped resources. Verified absence is success. The reaper uses a physical-only scope and leaves workspace, snapshots and replacement compute alone. |
| `observe` | Read without activating compute. Return exact incarnation evidence, its observed phase and any durable operation receipt, or proven absence or unknown. An unavailable or revoked account, missing host/App/image, or ambiguous inventory is unknown. |
| `listInventory` | Page through physical inventory within the bound provider account or host. Each entry carries deployment, sandbox, generation, immutable physical identity and creation time. This is an observation, not permission to delete. |

Adapters implement idempotency at the provider or host boundary, including delivery after a transport timeout. An adapter may store a receipt or journal an intent. It holds no sandbox lease, renews none and owns no independent retry timer. An observed absence is sufficient for a repeat only if the adapter proves that a prior dispatch cannot still take effect or that the same operation key deduplicates it. An operation for an old generation must be rejected or restricted to that old incarnation even if it reaches the provider late. If the provider cannot prove those properties for a path, leave that path out of job cutover until its adapter can. In particular, a local database CAS cannot fence a remote mutation by itself.

The capability record describes the enrolled runtime path. Availability can still depend on the bound account, image, host and retained state. `humanSsh` means a user-facing pinned SSH session, and `resourceSampler` means an attested read without resuming compute. `sizes` is the set of selectable catalog sizes.

| Capability | Boat | Modal | Docker |
| --- | --- | --- | --- |
| `maxTtlSeconds` | 2,592,000 | 86,400 | 86,400 |
| `stopRetention` | `disk` (provider-retained VM disk) | `image` (recovery image) | `container` (host-local retained workspace) |
| `snapshots` | `required` (pinned golden revision) | `optional` (immutable snapshot or admitted base image) | `optional` (host-local snapshot or plain image) |
| `extendLifetime` | Yes | Yes, within admitted provider headroom | No |
| `humanSsh` | Yes | Yes, for supported SSH configuration | No |
| `resourceSampler` | Yes, attested VM | Yes, attested explicit VM | No |
| `sizes` | small, medium, large, xlarge | small, medium, large, xlarge | Empty, host policy applies |

| Provider | Launch and bootstrap | Retained stop and resume |
| --- | --- | --- |
| Boat | Fork a pinned golden revision, then bootstrap the Armada runtime. Reconcile by verified provider receipt. | Verify the retained VM and restore under the next generation. Boat verification is coordinator-only. |
| Modal | Allocate or adopt by generation from a pinned image, then bootstrap the runtime. | Checkpoint the exact runtime, persist the recovery image before termination, and restore that image into the next generation. |
| Docker | Use the authenticated outbound daemon job and receipt protocol for the plain image and host-local snapshot paths. | Confirm host job receipts. Retain and restore the workspace on its bound host, with a generation-checked handoff. An offline host leaves the result unknown. |

The provider-run paths on Boat and Modal drain and are deleted under Step 1. Specialized golden-build and access paths remain governed by their own contracts. Replace each covered lifecycle path in its rollout ticket without fallback dispatch after the switch. Database and runtime/daemon protocol changes observe the N/N-1 overlap. A schema drop follows deployment of the last code removal.

## Runner and ownership

- Admission commits the sandbox, request receipt and launch job in one transaction before any external dispatch. Freeze the provider binding, image, desired retention or restore reference, compute TTL, caller and initial turn intent as applicable. Keep secret material as references or encrypted payload. Scope the launch request key to organization, authenticated owner and operation. Record a canonical digest of the normalized request, excluding secret values and including stable references for credential selections. Replay must pass current visibility and authorization checks and match the stored digest before returning the original sandbox. A mismatch is a conflict. An initial prompt is a separately durable turn intent keyed to the accepted launch job and its generation, so replay cannot admit it twice.
- Only the sandbox lifecycle module writes sandbox status. The runner holds the claim for the single active lifecycle operation. Each operation has one persisted absolute dispatch deadline in `deadline_at`. The deadline survives takeover and is shorter than the 15-minute reaper grace for launch and resume. Renewing a lease never extends the deadline. Lease expiry governs worker ownership, and compute TTL governs resource lifetime. Neither authorizes another dispatch after the operation deadline.
- Launch starts at the sandbox's initial generation. Resume bumps exactly once in the transaction that enqueues it. Stop and delete address the current generation. At most one unresolved lifecycle intent can dispatch for a sandbox. Use a sandbox row lock for admission and handoffs. A stop or delete racing launch/resume records cancellation of that intent under the same lock and waits for reconciliation before dispatching conflicting work. A successor reconciles the old outcome before replacing a generation. Explicit and implicit resume share the same intent.
- At each external dispatch, verify the claim, phase, generation and remaining deadline. Re-check current authorization before fresh allocation. An expired, cancelled or revoked intent may still reconcile prior calls via authorized management, but cannot allocate, bootstrap, publish readiness or send its initial turn. Record failure or cancellation and the unresolved resource reference if necessary. Keep ownership until exact observation or the existing cleanup lane resolves it. Never turn an uncertain outcome into absence just to finish a job.
- During the target flow, only the current or an expired claim's successor in the jobs runner can hold the sandbox lease. API admission, runtime enrolment, telemetry, output capture and inventory reconciliation acquire none. Enrolment and cancellation still serialize against lifecycle changes via short database transactions and generation checks. An older worker can still receive a response after lease loss, but cannot commit it. Legacy worker claims, Modal source/child leases and the launch golden fence must be gone from a converted path before the jobs runner owns it.
- Pin the immutable snapshot reference at admission. Launch admission and snapshot retirement serialize on the same snapshot record in short transactions. Retirement checks for live generation, pending job and retained recovery references, and persists a tombstone before remote deletion. Admission refuses a tombstoned snapshot. Concurrent launches share the reference and release the database lock before boot. There is no golden fence or boot-long source lease.

### Jobs table and claim

`jobs` contains `id`, `kind`, `sandbox_id`, `org_id`, `generation`, unique scoped `idem_key`, `request_owner_id`, `request_digest`, `state`, `run_after`, `deadline_at`, `attempts`, `max_attempts`, `lease_owner`, `lease_epoch`, `lease_until`, `payload_enc`, `outcome` and `created_at`. The lifecycle phase and provider evidence live in the job outcome, separate from claim state. Deadline and sandbox identity are required for lifecycle jobs. For launch, require the owner and request digest. Derive the stored key from an unambiguous encoding of organization, owner, operation and caller key, or a server-generated request ID for unkeyed admission. Internal jobs use a separate key namespace scoped by kind, sandbox and generation. Scope the table and claim functions to the service role. Return safe codes and correlation IDs in public status, never provider error bodies.

The existing worker scheduler runs the jobs lane. Claim due jobs from registered kinds using `FOR UPDATE SKIP LOCKED`, ordered by due time and ID. Serialize lifecycle claim selection against the sandbox row and enforce one leased lifecycle row per sandbox with a partial unique index on leased lifecycle rows. Take over an expired lease on that same row, increasing its epoch. Renew only under the matching owner, epoch and generation before expiry. Each claim counts as an attempt. Any phase update, renewal or completion after a lost lease is a no-op. Completion CAS checks job id, owner, epoch, unexpired lease and current generation. A stale generation is retired by the runner without dispatch. Do not overwrite a newer sandbox state when a CAS matches zero rows.

| Handler result | Runner action |
| --- | --- |
| `done` | Commit completion and release the claim, atomically with any remaining lifecycle effect. |
| `retry(after)` | Preserve evidence, set `run_after`, release the claim and let the existing lane pick it up. Bound redispatch by attempts and the absolute deadline. |
| `fail(reason)` | Commit a typed terminal outcome and release the claim. Record unresolved ownership explicitly and hand off to existing cleanup in the same transaction when needed. |

Each kind has a configured concurrency ceiling across replicas. Use a short per-kind transaction lock to serialize the capacity check with claim allocation. Count active unexpired claims before admitting another. The lock is released at commit and never held across a handler. A takeover gets an abortable handler; loss of renewal aborts it and leaves the durable intent for its successor. Enqueue wakes the existing lane after commit. A crash before the wake is covered by the existing scan schedule. Handler replay after its last checkpoint is safe even if completion never committed.

## Lifecycle states and crash recovery

Provider phases and turn activity do not define sandbox readiness. The sandbox module accepts enrolment for the authenticated current generation only while its intent is valid. It atomically records the runtime binding and `starting → ready`. Enrolment may arrive during bootstrap; the runner must have persisted dispatch intent first. Serialize enrolment against cancellation and verify the enrolled incarnation against the admitted binding. The turn lane dispatches the initial intent only after enrolment and required configuration commit. Claim it under the same sandbox row lock used for lifecycle admission, matching the accepted launch job, generation and eligible runtime binding. Stop, cancellation and replacement invalidate an undispatched initial intent in that transaction. A command already in flight is reconciled by its stable turn ID and can only reach the matching generation.

Every row below describes an await after a durable write. Provider and host calls that contain several durable substeps follow the same intent/receipt rule for each substep, including snapshot creation and termination.

| Flow and durable state | Next await / trigger | Writer and next state | Recovery after interruption |
| --- | --- | --- | --- |
| Launch admission commits sandbox `starting` and queued job | Send receipt or wake; claim | Runner leases launch job | Request replay returns the original sandbox. The existing lane finds a missed wake. |
| Launch claim commits | Read authorization and bound inputs; write create intent | Runner records `creating` | Take over the same job. Revalidate before dispatch. |
| `creating` committed | `create`, then persist physical identity | Runner records allocation, still `starting` | Observe by the current generation. Adopt proven allocation, retry with the same key when safe, or preserve unknown for reconciliation. |
| Launch or resume allocation committed | Write bootstrap intent and `bootstrap` | Runner records bootstrap outcome, still `starting` unless enrolled | Re-observe, reconcile runtime binding and replay the same bootstrap where needed. A receipt cannot mark the sandbox ready. |
| Bootstrap intent or outcome committed | Receive enrolment; read binding or retry observation | Sandbox module writes `ready` only on valid enrolment | Repeated enrolment of the same incarnation is idempotent. At expiry, fail unready intent and reconcile compute. |
| Enrolment committed | Wake turn dispatch; complete job | Runner completes job; turn lane claims durable initial turn | A missed wake is recovered by scanning. Turn identity survives retries and duplicate admission. |
| Stop admission commits `stopping` and stop intent | Claim, check exact incarnation and retention | Runner records stop dispatch intent | Reclaim under the same generation. Do not promote an unverified stop. |
| Stop dispatch intent committed | Within stop preparation, run one bounded final live read before `stop({retain})` | Runner records the staged capture or its timeout/refusal, then records the physical result | Reuse a durable staged result keyed by stop intent and generation. At cutoff proceed with stop. The output lane publishes the staged data independently. Reconcile the retained checkpoint and physical exit separately. |
| Retained checkpoint intent committed | Checkpoint/snapshot, persist retained reference, then terminate | Adapter records receipts; sandbox module writes `stopped` on confirmed exit and, if requested, verified retention | Resume the stop from durable evidence. Preserve the source on ambiguous checkpoint outcome. After exit, use the retained-output reader when available. Missing retention must be reported explicitly. |
| Resume admission commits `stopped → starting`, next generation and resume job | Claim, revalidate retained input, record restore intent | Runner records `restoring` | Concurrent resumes share the job and generation. Keep the predecessor until the new physical result is durable. |
| `restoring` committed | `resume`, then persist replacement identity | Runner records allocation and follows bootstrap/enrolment above | Observe the new generation. Adopt the replacement or retry the same restore only when safe. An old enrolment cannot ready it. |
| Cancellation, expiry or definite failure committed | Observe prior dispatch and persist outcome or handoff | Sandbox module records failure for an unsuccessful launch/resume; the runner preserves unresolved ownership for cleanup | Successors inspect by generation. Stop remains `stopping` while exit is unknown. A retry limit ends redispatch, not reconciliation. |
| Delete intent committed for a terminal sandbox after conflicts settle | `delete` and confirm exact generation absent | Sandbox module records `deleted`, then allows metadata and archive retirement | Re-observe and repeat the exact deletion. Never drop durable ownership before verified physical deletion. |
| Retry, checkpoint or completion committed | Wake, return or drain | Runner frees the lease on retry/completion | A crash loses only the wake or reply. A stale worker can neither publish state nor clear the current claim. |

Retention checkpointing is required when requested and supported. Under #2763 the runtime final read is stop preparation, so files written since the last sample can be staged before compute exits. Start it within the existing stop preparation budget, cap it inside the single operation deadline and reserve time for provider stop. A timeout or refusal ends the attempt and does not prevent stop. Output publication, export and retained reads run separately after the transition, under their own I/O deadlines. Stop admission and provider dispatch never wait for that publication. For retained stops, the checkpoint must preserve the output files needed by the retained reader.

## Client receipt and table retirement

By the end of Step 2a, launch through the existing operation returns accepted with `{ sandbox: { id, status: "starting" } }` (HTTP 202 on REST). The ID is the stable Armada sandbox ID. A keyed replay identifies the same sandbox and reports its current state. The launch receipt has no prompt ID, including after replay. A supplied initial prompt is admitted durably and dispatched via the turn lane after enrolment. Clients use sandbox status/events to see enrolment, timeout or failure before a turn, and turn APIs/events for the subsequently assigned prompt ID. Controls that need an enrolled runtime return a typed not-ready refusal while it is unavailable. Stop and delete use the Armada ID even while allocation is uncertain.

#2773 owns the common envelope and Docker idempotency/correlation inputs. #2760–#2762 switch admission and update the SDK types, CLI JSON and wait behavior, REST/OpenAPI and MCP schemas/guidance, dashboard, iOS, Armada skill and coordinator command references with each affected surface. Automation uses the sandbox ID from the receipt. There is no parallel async route, synchronous fallback or old receipt decoder.

Use `jobs.payload_enc` for new launch payloads. Completed launch jobs keep the minimal scoped key, digest and outcome as durable receipts even after clearing payload and retiring sandbox metadata. The [ordinary launch receipt contract](launch-idempotency.md) has no expiry. Preserve successful receipts, terminal refusals and keys with unresolved outcomes. A key reserved for a launch that cannot be proven absent must stay reserved.

Stop old producers for each switching path and drain their in-flight admissions before enabling the replacement producer. Backfill the new receipt representation from `ordinary_launch_receipts` and the durable Docker request and sandbox ownership records. Preserve the existing caller and organization scope, request identity and fingerprint, original sandbox ID or refusal, and any unresolved ownership. Keep the distinct ordinary and Docker request namespaces, so migration cannot collapse existing keys. Backfill as non-dispatchable records and verify every source key resolves to the migrated outcome before enabling the new producer. Where source identity or exact matching cannot be proven, refuse admission for the affected scope pending reconciliation. Never reinterpret absence from the new receipt store as permission to allocate during the backfill. The switched path reads only the new store and returns the new receipt shape.

The database overlap keeps prior tables available to old binaries with exclusive admission ownership per path. #2765 deletes synchronous paths and old request workers. #2766 drops `provider_launch_requests` and `docker_launch_requests` one deploy after their last code use. Retirement of `ordinary_launch_receipts` is outside #2766 and requires its own dependency check and later migration. Host daemon transport jobs and receipts remain the adapter's durable protocol, separate from runner claims.

## Pending risks and scope

[AR-01 through AR-04](accepted-risks.md) are pending owner sign-off under #2732. This design does not use a pending risk as an exemption.

- **AR-01:** Fresh create requires current authorization. One already-dispatched allocation can finish during revocation and is bounded by enforced compute TTL. Revalidate before bootstrap, enrolment publication and turn dispatch. If the binding cannot enforce TTL or reconcile safely, it is ineligible for cutover.
- **AR-02:** The new launch path commits ownership before allocation. For leftover orphan compute, use the existing #2725 sweep. Delete only an exact physical machine tagged to this deployment and strictly older than 15 minutes. Immediately before deletion, a fresh authoritative read must show no sandbox row, launch request, launch job or resume reference. Also prove that delayed admission or restore cannot attach the candidate after that read. Ambiguity, read failure or missing proof means keep it. Deletion is idempotent and compute-only. The grace interval sets eligibility, and actual cleanup depends on enabled inventory deletion and sweep success. Enforced compute TTL is still required for the stated risk bound.
- **AR-03:** Webhook delivery stays on its existing contract, with a stable delivery ID, at most five attempts and receiver-side atomic deduplication. Lifecycle replay does not add a sender or reissue a delivery with a new key.
- **AR-04:** The budget design in #2818 owns admission refusal at the ledger cap. Replayed lifecycle jobs do not admit additional launches or turns. Any overrun under that policy is limited to work already admitted when the cap was reached.

This note changes no code, schema, runtime protocol or deployed behavior. Native retirement, golden builds, webhook jobs, budget implementation, Step 3 status and event redesign, and deployed provider evidence belong to their respective tickets. Downstream implementation tickets own deterministic fault injection at the durable boundaries above. Boat stays outside CI and staging acceptance.
