# Official Docker sandbox image

Issue #1528. Registry: **GHCR**, package
`ghcr.io/the-vibe-company/armada-sandbox`. Only the release workflow publishes,
only for a validated release tag, and only `linux/amd64`. PR CI never builds it.
There is no `latest` alias: a release records `version` and `image@sha256:…`
in the `official-sandbox-image` workflow artifact. Release binary jobs download
that pin into core before compiling CLI/server, so `officialSandboxImage()`
returns that version's digest. Source/dev builds without a release pin retain the
server-owned immutable bootstrap baseline; see `docker-staging-image-compatibility.md`.
A present but invalid or mismatched release pin still fails closed.

The final image contains no checkout, credentials, enrolment tickets or account
environment. It contains build tools from buildpack-deps, Git, gh, Python, CA
roots, Node/npm, pinned Bun, and the public compiled runtime and all three harness
artifacts generated by the existing verified publisher. UID/GID 1000 owns
`/home/user`, the persistent Docker volume mount. It runs without root. Public
artifacts live under `/opt/armada`; they are not yet wired to per-sandbox caches.

## Owner prerequisites

- Allow this repository's `GITHUB_TOKEN` to write organization GHCR packages.
  The release job has `packages: write`; no PAT or new repository secret is needed.
- After first publication, make the GHCR package **public**, and retain repository
  Actions access. Hosts must pull anonymously; never distribute a registry token
  into guest images or launches. Confirm anonymous pull before rollout.
- Retain published version tags/digests for old snapshots. Recovery reuses an
  existing version tag's digest rather than replacing its image. Do not manually
  retag or delete a released image.

## Implementation and acceptance status

The release image, normal launch policy, snapshot provenance and explicit rebuild
flow are implemented. Do not restore the superseded snapshot catalog/UI branches:
version recording was consolidated into #1497, and #1574 added the update offer.

| Requirement | Implementation / operator reference |
| --- | --- |
| Release-only, immutable official image | `images/sandbox/Dockerfile`, `.github/workflows/release.yml`, `packages/core/src/official-sandbox-image.ts` |
| No normal user image selection | Normal launch policy below; [source-deployment compatibility](docker-staging-image-compatibility.md) |
| Snapshot records and lists its built-on version | [Host-local snapshots](docker-snapshots.md), including migration prerequisites |
| Dashboard and CLI offer an explicit rebuild | [Updating an older snapshot](docker-snapshots.md#updating-an-older-snapshot-1528) |

These paths are not evidence of deployed acceptance. After a publishing release,
the coordinator must verify on the owner's host:

1. Inspect the release's recorded GHCR digest and `linux/amd64` architecture;
   confirm anonymous pull, UID 1000 workspace ownership, tools and absence of
   checkout/secrets in the bare image.
2. Launch **Armada default** without an image input and confirm that the admitted
   image matches the deployed server's release pin, not the client's version.
   Use the existing [real-host lifecycle check](docker-snapshots.md#coordinators-one-real-host-acceptance-check)
   for snapshot build/launch evidence; do not substitute assistant claims.
3. Keep a ready snapshot built on an older stable version. Confirm its built-on
   version and update offer in the dashboard and CLI. Explicitly rebuild it and
   confirm a new snapshot uses the deployed version while the old one still
   launches. Nothing should rebuild automatically on upgrade.

Staging acceptance covers owner-enabled Modal and Docker probes only; Boat is
not part of the release gate. Any Boat production verification is coordinator-only
and separate from this Docker image acceptance. Workers do not publish, deploy,
apply migrations or operate the owner's host.

## Slice 2: normal launch policy

Normal API requests, CLI launches and dashboard forms no longer accept an image.
New Docker template definitions select a host only. Historic template image
fields are ignored at launch; existing sandbox/resume bindings are untouched.
The server chooses `officialSandboxImage()` from its own release, never from the
client's CLI version. A deployment with no generated pin uses the pre-transition immutable bootstrap
baseline so main-between-releases remains usable; it does not invent a GHCR digest. Exact request retries retain the admitted
image even if the server's release pin changes.

The release workflow carries the generated public pin into both release staging
and production source archives before Railway builds the server. Direct source
builds outside that release path need the same generated
`packages/core/src/official-sandbox-image.json` for their package version before
building; the checked-in null file is not a production pin. Do not manually
invent a digest or use a different release's pin. The operator lifecycle helper's
`--image` is now an expected-image assertion for normal launches, not a selector;
only its existing private preview route still sends it.

Host fetching and plain fetch-failure reporting are owned by #1525; this slice
adds dashboard progress but does not duplicate the host pull implementation.
Public artifact cache seeding/launch optimization remains follow-up work; the
existing verified bootstrap remains authoritative.
