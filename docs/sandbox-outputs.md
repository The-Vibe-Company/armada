# Sandbox outputs

Write deliverables as regular files directly inside `/home/user/outputs` on Boat, Modal and Docker. Create the directory as the agent if it is absent. Use the absolute path in prompts and scripts, including after resume. A harness may set its own home, so shell home expansion can point elsewhere. Armada includes the absolute path in the initial Boat and Modal launch prompts. This fixed directory is the declaration. The API accepts filenames for downloads and has no caller-supplied directory. Subdirectories, symlinks, hard links and special files are excluded. Use short filenames without control characters.

The previous Boat and Modal declaration, `/workspace/outputs`, assumed agents could create `/workspace` at the filesystem root. On the Modal staging golden, Claude Code received permission denied when it tried to create that parent. Use the new path in prompts and scripts. If a live Boat or Modal sandbox has deliverables under the previous path, move them to the new path for subsequent captures. While the new directory is absent, Boat and Modal retain any previous snapshot. Create an empty directory at the new path to publish an empty snapshot.

- **Modal** runs Claude Code, Codex and OpenCode on the native path through the image's runner as the Linux `user` account. The enrolled runtime starts as the owner of `/home/user` (also `user` in the Armada image), and its Claude Code, Codex and OpenCode drivers inherit that identity. The image creates `/home/user` and assigns ownership to that account. The filesystem root is root-owned, and the golden image recipe does not provision `/workspace` or grant ownership of it to the agent.
- **Boat** launches native Claude Code and Codex through Boat's prompt API, which manages their process identity. Armada's native setup uses Boat's `user` home at `/home/user`. Native OpenCode is unsupported. On the enrolled path, the Claude Code, Codex and OpenCode drivers run as the owner of `/home/user`, normally `user`. Boat supplies the golden filesystem, and Armada's builder does not provision `/workspace` or make the filesystem root agent-writable. The native effective UID and the ownership of `/workspace` on individual Boat goldens require live provider evidence.
- **Docker** runs agents as UID and GID 1000 without privilege escalation, with a retained volume at `/home/user`.

Using the writable home lets agents create the same directory on demand across providers and avoids changing ownership or adding launch and resume steps.

Each snapshot admits up to 32 regular filenames in bytewise name order. An individual file may be up to 32 MiB, and each published sandbox snapshot may contain up to 64 MiB of file bytes. Each organization has a 1 GiB reservation budget shared by all its sandboxes, including published and in-progress revisions. A replacement reserves its new bytes while the previous version remains downloadable. When the organization is full, an existing version stays published while its replacement waits for space. A quota check reclaims unpublished revisions after 15 minutes without transfer progress. Files that exceed a byte limit appear in the list with a skip reason. A directory with more than 4096 entries is not read at all. A failed or out-of-bounds read keeps the previous snapshot; it never blocks a stop or the shared worker. Periodic samples run in the background with a 25-second deadline, with up to four live samples across providers, so the shared worker loop never waits for a provider read. An outstanding sample that passes its deadline counts only against its own provider’s four-sample limit. The final pre-stop capture waits only until the shared pre-stop budget, from its scan claim on (a claim held by a row lock or a pool connection counts, and a claim that returns late never reaches the provider), even when the provider SDK ignores cancellation; a capture that outlives it stays tracked, and new final captures are skipped only for the provider with four such late captures outstanding. No read persists after its deadline: the deadline is checked again under the row lock and after the write, before commit, so time spent waiting for the database counts and an expired write rolls back with its webhook events.

## How outputs are read

Supported providers are Boat, Modal and Docker. On Boat and Modal, both native and enrolled-runtime sandboxes (Boat runtime, Modal dial-out), the server reads the directory through fixed manifest and range reads of live compute. It never runs caller commands, never goes through the agent runtime and never starts or resumes compute. A fixed collector reads the live disk without following symlinks; it uses the Bun executable provisioned by Armada (Bun 1.4.2 at the root-owned `/opt/armada/runtime-bun/bun`: the managed runtime Bun on Modal, and on Boat a copy the golden build installs from the Armada pin, never from the repository's Bun pin), Linux glibc, GNU `stat` for the managed executable ownership check, and the Linux descriptor filesystem at `/proc/self/fd`. The shared golden builder checks these capabilities after repository setup and before taking the snapshot, and fails the build unless the probe prints its fixed answer: an incompatible Bun can exit 0 without running the program. At run time the same answer is required, otherwise the sandbox is marked `collector_unsupported`.

Boat sandboxes launched from goldens built before this change have no managed Bun. To keep their outputs collecting after an upgrade, an unprivileged collector falls back in order. First it tries a guest Bun at a fixed path (`/usr/local/bin/bun`, `/usr/bin/bun` or `/home/user/.bun/bin/bun`), but only after that Bun evaluates a test expression. A repository-pinned Bun that prints its help and exits 0 is skipped. Then it tries the earlier `python3 -I` reader (`/usr/local/bin/python3` or `/usr/bin/python3`). Both fallbacks keep the same bounds, exclusions and exit codes. A privileged exec never runs the agent's Bun. It runs Python only when the resolved executable and its parent directories are root-owned and not group- or world-writable. The golden build checks the managed Bun alone. A fallback never satisfies that check. Rebuild a golden to give its sandboxes the managed reader. Boat runs it through its command API. Modal runs it on the physical container, so enrolled runtimes that refuse server exec are covered too.

Docker sandboxes have no provider exec: the host daemon only manages the machine, and the only server-to-sandbox channel is the enrolled Armada runtime. The server queues the runtime's fixed, read-only `readOutputs` operation (no caller command or path) under the owner's live runtime fence. The runtime reads the directory with the same bounds and exclusions, opening the directory and every file without following symlinks; it needs no Python. A read expires at its 25-second deadline, which is carried in its request ID: an expired read is never dispatched to the runtime and never counts as pending work, so it cannot hold user commands or the idle checkpoint behind it. When the next output read for the sandbox starts, it deletes every earlier read row nobody can still use: its runtime epoch ended, or it is past its deadline and the runtime answered a later command. The runtime answers in order, and a read is never dispatched after a later command was answered. So samples do not accumulate as runtime history. Deleting a row the runtime may still acknowledge would make that acknowledgement fail. While the runtime stays unreachable, each sample leaves one expired row; the next read after the runtime answers again or its epoch ends deletes them. After a chunk is consumed, its reply is replaced by a small encrypted acknowledgement receipt. An expired read is acknowledged without storing the file bytes, and physical stop clears any remaining output replies. A read is skipped, keeping the previous snapshot, while a non-output runtime command or two unexpired output reads are still unanswered, because the runtime answers its queue in order. Agent self-finish validates its runtime epoch and MCP generation before the final read, which runs only under that epoch. A read queues behind a single in-flight output read, so a pre-stop capture taken during a periodic sample gets its own fresh read before the stop is admitted; once a stop is admitted the runtime fence refuses the sample's late reply. Sandboxes whose runtime supports the original output operation fall back to 32 KiB snapshots until relaunched with the chunk-capable runtime. Sandboxes from before the output operation need a relaunch to collect any outputs.

- **Running sandboxes** are sampled approximately every 30 seconds.
- **Armada stops** (user, managed-child, idle, expiry, agent-finished and credential-migration stops, including a user stop of a `failed` sandbox, whose compute may still run) take a final live snapshot before provider stop is dispatched, after the agent is quiesced where work preservation runs. If that capture fails or its shared pre-stop budget is exhausted, the last successful sample remains. Before the first periodic read, Armada claims one capability probe per sandbox and records whether the collector is supported. Final capture never waits for a probe: its bounded read is the last chance to collect a deliverable, and the read's own result classifies an unsupported collector. When a probe or read reports that collection is unsupported, Armada skips subsequent periodic and final reads, so a final capture adds no delay to stop. Transient failures remain retryable. Armada logs each reason at most once per sandbox.
- **Armada Docker stops** (user, idle and agent-finished) take the final snapshot, bounded to 12 seconds, before the stop job is queued: once a stop is requested the runtime refuses commands. Docker stops queued by a host uninstall or the host-bound preview API rely on the last sample.
- **Stopped sandboxes are never read**, on any provider. Their downloads serve the last snapshot taken while compute was live.

### Known limits

Large files can require several sampling passes, especially on Boat. A newly written document may need more time than the final stop window provides. A pass begins with a fresh manifest and continues a partial revision at its last saved offset. Changing or replacing a file invalidates progress on its old revision. An interrupted capture keeps the previous snapshot available. A final capture still shares the existing stop deadline, so finish writing large files while the sandbox is running to allow time for collection.

Files written or changed after the last capture are not collected. This covers files written between the last 30-second sample and a stop Armada did not initiate (Boat TTL, Docker host expiry or uninstall, or a provider-initiated stop), and a background writer that finishes after the final pre-stop capture. Armada does not reread a stopped sandbox's retained workspace (Boat disk snapshots, Modal recovery images); that is tracked in #2609. Until then, finish writing deliverables before the agent's turn ends.

Application-secret exposed (tainted) sandboxes are never read. Their existing snapshots are purged when taint is recorded, and their outputs routes return 404, matching the exec and work-recovery refusal. Taint is checked again immediately before every provider read, after the scan claim. Under the runtime session lock, Docker never admits or dispatches an output read once taint has committed. A reply to a read issued before taint is acknowledged so the runtime queue advances, but its file bytes are not kept.

## API

Authenticated owner/admin callers can use:

- `GET /api/v1/sandboxes/{id}/outputs`: the sandbox's declared directory, policy limits (`maxFiles`, `maxFileBytes`, `maxSandboxBytes`, `maxOrgBytes`) and file metadata (`name`, `size`, `sha256`, `updatedAt`). Skipped files have `sha256: null` and `skipped: "too_large"`, `"sandbox_limit"` or `"org_limit"`. A sandbox with an unsupported collector also returns `unavailable: "collector_unsupported"` and retains any previous snapshot.
- `GET /api/v1/sandboxes/{id}/outputs/{encodedName}`: streamed attachment bytes, content type, length, nosniff and private/no-store headers. A single HTTP byte range returns 206. Invalid or unsatisfiable ranges return 416. Skipped entries return 404. If a replacement or access revocation interrupts a stream, the client can fetch the list again.

Collected snapshots are encrypted using `ARMADA_ENCRYPTION_KEY` and stay readable after stop without contacting the provider. Deleted sandboxes are inaccessible. A new snapshot replaces the previous file set; files removed from the directory disappear on the next successful read. Reads are ordered by when they were started: a read never replaces a snapshot from a read started after it, but a sample still in flight when a final capture fails still publishes, if its reply can still be delivered. The bounded last snapshot is kept until the sandbox row is purged.

Each new or changed file emits `sandbox.output.available` through the existing signed webhook outbox, in the same transaction as persistence. Payloads include the sandbox/org IDs, external reference and output name, size and SHA-256; no document bytes. Unchanged files do not emit duplicate events. Webhook receivers should fetch using their existing Armada token and handle ordinary at-least-once delivery.

## Design decision

Provider exec was the only file egress path, and it is gone once compute stops. The server collects a manifest and bounded ranges while compute is live and once more before Armada dispatches a stop. Boat reads at most 32 KiB per response to fit its command output budget, with up to eight reads in flight per capture. Modal and Docker can read up to 512 KiB per response. Armada stores encrypted 32 KiB chunks in separate rows so collection can resume across worker restarts and download can stream with backpressure. It publishes the file list and availability webhooks in one transaction after every admitted revision is complete. That gives downloads after stop without arbitrary filesystem reads or waking stopped machines. Outputs are opt-in by writing to the declared directory; do not put credentials there.
