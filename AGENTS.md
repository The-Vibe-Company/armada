# Repository instructions

Armada v2 launches coding agents (Claude Code, Codex) on boat.dev sandboxes: a remote MCP server for orchestrators and the `armada` CLI, in one binary. It is a launcher, not an orchestrator. The specification is issue #455; read it before changing behaviour.

Armada v1 (the fleet orchestrator) is archived at the tag `armada-v1-final`. Its code is not on `main`; bring a piece over by hand when v2 needs it (`git show armada-v1-final:<path>`), never by restoring whole folders.

## Layout

- `packages/core` (`@armada/core`): the shared contract (types, the version). No network or database I/O. `src/provider.ts` is the `Provider` interface (goldens, sandboxes, prompts, events by cursor), the common `AgentEvent` stream, per-harness capabilities and `ProviderError`. `src/golden-config.ts` is the versionable golden file (repos, branches, init; secret keys refused) and the namespaced boat snapshot name. `src/golden.ts` builds, connects and snapshots a golden through a `Provider` and a `GoldenStore`; `goldenForLaunch` is the lookup launch uses. `src/golden-store.ts` is that store over SQL, under the caller's database role. `src/crypto.ts` seals `*_enc` values with AES-256-GCM (`iv || ciphertext || tag`) under the single env name `ARMADA_ENCRYPTION_KEY`; the dashboard and credential resolution (#461) both call it. `src/credentials.ts` resolves credentials for a launch (user over org) and `src/vault.ts` holds the org, member and credential rules over a service-role `VaultStore`. `src/github.ts` is the GitHub identity of a launch: the App's user-to-server OAuth (code exchange, refresh with rotation by compare-and-swap, revocation), `resolveGitHubAccess` and the git setup command run in the sandbox. `github_connections` holds the sealed refresh token per user; setup in `docs/github-app.md`. `src/database.types.ts` is generated from the Supabase migrations (`bun run db:types`).
- `supabase/migrations`: the Supabase CLI migrations. Schema first, then row level security. A fresh Supabase database already has `auth.users`, `auth.uid()` and the `authenticated` and `service_role` roles. `goldens.boat_sandbox_id` is the master sandbox; `boat_snapshot_id` is the namespaced saved-snapshot name, null until snapshot. `oauth_clients` and `oauth_codes` are the MCP authorization server, writable only as `service_role`. Supabase grants `ALL` on every new public table, sequence and function to `anon` and `authenticated`, and a column grant only adds to that; `20261108190000_revoke_default_grants.sql` revokes it (and those default privileges), so `anon` holds nothing and a new table or column is reachable by a user JWT only through an explicit grant. `scripts/db/supabase-prereq.sql` reproduces Supabase's defaults so the tests see them. A user JWT selects no `hash` or `*_enc` column (`20261108200000_token_hash_column_grants.sql` narrows the token tables), so any user-JWT request that writes a row names the columns it returns with `select=`: a bare PostgREST insert returns `*`.
- `packages/provider-boat` (`@armada/provider-boat`): the boat.dev provider adapter over `@boatdev/sdk` (`createBoatProvider`; `src/errors.ts` maps boat errors, `src/events.ts` normalizes events). `createGolden` always sends `noEnv: true` and never an account environment. Unit tests run the real SDK against a fake `fetch`; `test/integration.test.ts` is opt-in (`BOAT_API_KEY`).
- `packages/core` also holds the launch flow: `src/launch.ts` (`launchSandbox`), `src/credentials.ts` (user over org), `src/sandbox.ts` (the sandbox store and the cleanup) and `src/outcome.ts` (a prompt's final status).
- `packages/auth` (`@armada/auth`): Supabase login, the MCP OAuth server, service tokens and bearer verification. Tokens are stored as lowercase sha-256 hex. The CLI keeps the Supabase session on the machine; the MCP server verifies bearers with the service role and does not cache them.
- `packages/cli` (`@armada/cli`): the `armada` command. `src/run.ts` takes its I/O as arguments; `src/main.ts` wires the process and is the binary's entry. `armada golden` creates, connects, snapshots and lists. `armada launch` forks a golden into a sandbox. Supabase is reached with the user JWT (`src/supabase.ts`), never a service role key. Golden commands read `BOAT_API_KEY` from the environment, never from the boat.dev account. `armada launch` resolves its model credentials and boat key from the encrypted store. `armada login` and `armada token` are the auth commands.
- `packages/mcp-server` (`@armada/mcp-server`): the remote MCP server that `armada serve` runs. `src/http.ts` is the handler (`/healthz`, the OAuth routes, the control API, `/mcp`), `src/tools.ts` the MCP tools, `src/turns.ts` the prompt status, wait and failure reason, `src/data.ts` the SQL reads and writes, which carry the visibility rule themselves because the server's connection bypasses row level security. `src/control.ts` is the control API for `armada org`, `armada creds` and credential resolution at launch (`handleControlRequest`, mounted in `armada serve`). Tests drive it through the MCP SDK client on PGlite with the real migrations and a fake boat. `Dockerfile` and `railway.json` deploy it.
- `apps/dashboard` (`@armada/dashboard`): the web dashboard (Next.js App Router, Tailwind, shadcn/ui). It acts as the signed-in user over Supabase (RLS applies), never with a service key. Pure logic lives in `src/lib` (tested with `bun test` in `test/`); `e2e/` is Playwright against `e2e/mock-supabase.ts`. Writes RLS cannot express go through the functions of `supabase/migrations/*_dashboard_functions.sql`.
- `scripts/build.ts`: compiles the binary with `bun build --compile` (linux and macOS, x64 and arm64).
- `scripts/npm.ts` stages the npm packages from those binaries: `@thevibecompany/armada` (the `armada` bin, the Node launcher `packages/cli/npm/armada.cjs`) and one `@thevibecompany/armada-<target>` per binary, as optional dependencies. `scripts/npm-smoke.sh` installs the packed tarballs with npm and Bun and runs them. `.github/workflows/release.yml` publishes on a `v<version>` tag of `main` (`docs/releasing.md`). `docs/dave-onboarding.md` is the production onboarding guide.

## Commands

- `bun install`
- `bun run verify`: lint (Biome), typecheck (`tsc`, strict) and tests (`bun test`). CI runs the same as "Lint, typecheck and test".
- `bun run format`: apply Biome formatting and safe fixes.
- `bun run build` (this machine), `bun run build --target <os-arch>`, `bun run build:all`: the binary in `dist/`.
- `bun run armada <args>`: the CLI from source.
- `bun run dashboard`, `bun run dashboard:build`, `bun run e2e`: the dashboard (dev, production build, browser tests). `bun run verify` typechecks it and runs its unit tests, not the e2e.
- `bun run db:types`: regenerate `packages/core/src/database.types.ts` after a migration change.

## Rules

- **One binary.** The CLI and the MCP server ship as the single `armada` executable from `bun build --compile`. Code in it may use Bun APIs; a dependency must bundle into it.
- **One version.** Every `packages/*/package.json` carries the same version; `@armada/core` exports it and `armada --version` prints it.
- **Secrets never in the repository.** Keys come from the environment or Armada's encrypted store; never print one, never write one into a file, a fixture or a log. Goldens hold no secrets. In the database a secret is ciphertext (`bytea`, `*_enc`) or a token hash, and a user JWT cannot read the ciphertext columns. One encryption scheme: `encryptSecret` and `decryptSecret` in `@armada/core` with `ARMADA_ENCRYPTION_KEY`. Credential values arrive on stdin or from a file, never as arguments.
- **Schema changes are new migrations.** Never edit a migration that has been applied. Row level security is the access rule: members see org resources, a private resource is visible only to its owner, and only an admin changes an org golden, the members or an org key.
- **Tests earn their place.** One test per behaviour at the cheapest boundary, no network, no wall-clock waits.
- **English** in code, CLI output, docs and comments.
- Pull request titles follow Commitizen, for example `feat(cli): launch an agent from a golden`.
