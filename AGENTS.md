# Repository instructions

Armada runs a fleet of coding agents on one project: Linear holds the plan and progress, GitHub holds the code, and the `armada` CLI gives the coordinator and the workers one shared reading of the fleet.

## Layout

- `packages/core`: `armada.toml` parsing, read adapters for Linear and GitHub, the one Linear write adapter (`linear-write.ts`, behind `LinearWriter`; tests use `FakeLinear` in `test/support.ts`), the fleet's live data (`live.ts`: the records, the `FleetStore` the app implements, what each command records and the inbox read; `fleet-api.ts`: both halves of `POST /api/cli/fleet/<operation>`, the CLI's `fleetClient` and the app's `serveFleet`, which checks each request and a worker session's scope), the machine store (`machine.ts`: keys and personal defaults under `~/.config/armada`), the pure fleet derivations (tickets in flight, frontier, pull requests waiting) and phase rules (`phases.ts`), the worker commands (`worker.ts`: claim, report, release), questions and the coordinator's inbox (`inbox.ts`: ask, inbox, answer), the dashboard's requests (`requests.ts`: answer and launch requests, checked before they are written), the launch brief (`brief.ts`) and the profile routing it and `claim` share (`routing.ts`: `[[conductor.routing]]` on the ticket's labels, `--profile` overrides with a reason), the coordinator's merge (`merge.ts`: checklist, merge lease, pinned merge behind the `MergeForge` and `LocalRepo` adapters), the Armada API client (`armada-api.ts`: `armada login`'s device code and polling, whoami, sign-out, the organization's Linear key, the organization's projects, the fleet operations; the address and the sign-in resolve in `credentials.ts`), and the repository setup rules shared by `doctor` and `init` (`setup.ts` over a read-only `RepoView`, `labels.ts` for the Linear label groups, `skills.ts` for the bundled skills). No I/O outside the adapters; network adapters take an injected `fetch`.
- `packages/cli`: the `armada` command. Side effects are injected through `Io` in `src/io.ts`; `src/main.ts` wires the real process; `src/bin.ts` is the entry of the published Node bundle.
- `packages/dashboard`: the live Fleet view (Next.js App Router), not published to npm. One Postgres database (Neon in production, PGlite in tests and local development) holds everything the app keeps: `lib/db.ts` (the `Database` interface over node-postgres or PGlite, `DB_MIGRATIONS` applied under an advisory lock, never Better Auth's automatic migration; `ARMADA_DATABASE_URL`), opened once per process by `lib/app-db.ts`; the fleet's live data is `lib/fleet-store.ts` (registry, events, runtime handles, inbox, leases with `SELECT ... FOR UPDATE`, coordinator presence). `lib/fleet-data.ts` orchestrates reads (Linear and GitHub cached per project, the fleet store on every poll) behind an injected `Sources`; `lib/server.ts` wires the environment; every fleet rule stays in core (`buildStatus`, `buildOverview` in `overview.ts`), imported through `@armada/core/read`, which leaves out the Bun-only skill imports. `lib/cli-api.ts` (routed at `/api/cli/*`, which both gates let through) is the API the CLI calls: device authorization for `armada login` (confirmed on `/device`), whoami, sign-out, `POST credentials`, `GET projects` and `POST fleet/<operation>` (every read and write of the fleet's live data: core's `serveFleet` on `fleetStore`, for a project the caller's organization holds, registered for it on first contact), with a session token, an organization API key or a worker session. No terminal holds a database key. The vault (THE-840): `lib/vault.ts` seals the organization's keys (AES-256-GCM envelope under `ARMADA_SECRETS_KEY`) in the app's database and keeps their audit list; `lib/broker.ts` hands the Linear key to terminals and the Linear and GitHub keys to the dashboard's own reads (`lib/server.ts`, per organization; only the first organization falls back to the environment's); the Keys page is `app/organization/keys` with `app/keys-actions.ts`. GitHub (THE-851): `lib/github-app.ts` is the Armada GitHub App (`ARMADA_GITHUB_APP_ID`, `ARMADA_GITHUB_APP_PRIVATE_KEY`): an app JWT, the installation covering each repository, installation tokens minted server-side and cached until near expiry; every GitHub read of the dashboard goes through it (`lib/server.ts`), a stored GitHub token only as fallback. The first organization reads through any installation, another only through those an owner or admin linked on `app/organization/github` (`app/github-actions.ts`), after GitHub listed them for that person; the same app's client id and secret sign people in. Workers (THE-841): `lib/workers.ts` keeps the one-time launch tokens `armada brief` asks for (`POST /api/cli/launch-tokens`: one ticket, used once, one hour, stored hashed) and the worker sessions they are exchanged for (`launch-tokens/exchange`, rate-limited per address); a worker session only gets keys and fleet operations for `claim`, `report`, `ask` and `release` on its own ticket and project, and ends on release, merge (`workers/end`) or Revoke on `app/organization/workers` (`app/workers-actions.ts`). Fleet writes are `lib/requests.ts` and `app/actions.ts` only: requests to the coordinator's inbox (answer, launch), checked by `core/requests.ts` over its `RequestStore`, never a runtime call. `scripts/db.ts` (`bun run db migrate|register`) applies the schema and registers a project from a terminal. `lib/demo/` is the synthetic demo world (`ARMADA_DASHBOARD_DEMO`, `bun run demo:seed`); strings live in `lib/i18n.ts` (English and French). Accounts (Better Auth: GitHub, email and password, organizations) turn on when the `ARMADA_AUTH_*` variables are set (`lib/accounts-settings.ts`); the instance is built in `lib/accounts.ts`, Better Auth run by the app on the app's database through `PgDialect` (Neon's managed auth has no device authorization, no API keys and no server hooks), the proxy rule is `lib/accounts-http.ts`, the server checks `lib/accounts-server.ts`, the forms `app/auth-actions.ts`. Until then `proxy.ts` keeps the shared `ARMADA_DASHBOARD_PASSWORD` gate (`lib/auth.ts`, `lib/auth-http.ts`, `lib/auth-server.ts`). Every server action and data read calls `requireFleetAccess()` (`lib/access.ts`) first: it gives the viewer's organization scope, and fleet reads only show that organization's projects.
- `skills/`: the skills `armada init` vendors into every managed repository (`armada-coordinator`, `armada-worker`, `armada-runtime-conductor`). `packages/core/src/skills.ts` imports each file as text so the published bundle carries them; a new file must be listed there too (a test compares the list with the folder).
- `docs/runbook.md`: how to start a coordinator on a laptop or in Conductor Cloud, and what the owner sets up once.
- `armada.toml`: this repository's own Armada configuration.

## Commands

- `bun install`
- `bun run verify`: lint (Biome), typecheck (`tsc`) and tests (`bun test`). CI runs the same on every pull request.
- `bun run format`: apply Biome formatting and safe fixes.
- `cd packages/cli && npm pack`: build `dist/armada.js` (Bun bundles `core` for Node) and pack the npm tarball. CI installs that tarball and runs it on every pull request.
- `cd packages/dashboard && ARMADA_DASHBOARD_PASSWORD=off bun run dev`: the dashboard on port 4822 (`off` works outside production only; without it or accounts every route answers 503); `bun run build` is the Vercel build and runs in CI. See the README for the demo mode and for running it with accounts (`ARMADA_DATABASE_URL=pglite:.demo/armada`, a local PGlite database). Dashboard tests run on PGlite; `ARMADA_TEST_DATABASE_URL` (a direct URL to a throwaway Neon branch, never production) runs the same tests on real Postgres, one schema per test file.
- `bun run armada status [--json]`: runs the CLI from source; needs `LINEAR_API_KEY`; GitHub uses `GITHUB_TOKEN`, `GH_TOKEN` or `gh auth token`.
- `bun run armada auth login|status|logout`: keys stored once per machine in `~/.config/armada/credentials`.
- `bun run armada login [--api-key]`, `whoami [--json]`, `logout`: sign this terminal in to Armada (`ARMADA_API_URL` points it at a local dashboard with accounts, e.g. `http://localhost:4822`). `armada login --launch-token <token> [--api-url <url>]` is a worker's first command: the token comes from the launch message `armada brief` prints when the coordinator is signed in; the worker session is kept per ticket (`ARMADA_WORKER_SESSION_<TICKET>` in the credentials file).
- `bun run armada claim|report|release|ask`: the worker commands; their live record goes through Armada when the terminal is signed in (`ARMADA_API_URL=http://localhost:4822` for a local dashboard with accounts), and is skipped with a warning otherwise.
- `bun run armada inbox [--wait]` and `bun run armada answer <item|ticket> "<text>" [--note]`: the coordinator's inbox (through Armada; `--wait` asks every 15 s and Armada answers 304 while it is unchanged) and how it records an answer it already delivered through the runtime guide. `answer` never calls a runtime.
- `bun run armada merge <pr> --dry-run`: the coordinator's merge checklist without merging. Never run `armada merge` without `--dry-run` from a worker: workers never merge.
- `bun run armada brief <ticket> [--profile <name>] [--prompt|--json]`: a worker's launch prompt and settings; needs `LINEAR_API_KEY`.
- `bun run armada doctor [--json]` and `bun run armada init [--program-root <ID>]`: check a repository (and whether this terminal is signed in to Armada), and open its setup pull request. Try `init` only on a throwaway repository: it pushes a branch, opens a pull request and creates Linear labels.

## Rules

- **Generic and open source.** No customer or private project names, data, thresholds or recorded responses. Fixtures are synthetic: invented ticket ids, titles and people.
- **Everything project-specific comes from `armada.toml`.** Program root, repository, label names and thresholds are configuration, never constants.
- **Secrets from the environment, Armada or the machine store, resolved in one place.** `resolveCredentials` in `packages/core/src/credentials.ts` picks each key (environment first, then the organization's keys from Armada when signed in, then `~/.config/armada/credentials`); only `packages/core/src/machine.ts` reads or writes that file. A secret stored by the dashboard goes through `lib/vault.ts` only, sealed, and no page or log ever receives its value. Never read tokens anywhere else, never print one, and never write one into a repository file, a fixture or a log. Tests point `XDG_CONFIG_HOME` at a temporary directory, never at the real one.
- **The CLI reaches the fleet's live data only through the Armada API** (`fleet-api.ts`), with the terminal's sign-in; no machine holds a database key. Every operation answers from Postgres with indexed queries, holds nothing open (no long poll: a waiting client polls, and gets 304 when nothing changed) and never calls Linear or GitHub. Every row carries its project slug, leases are scoped per project, and times are the server's. A new operation is added to both halves of `fleet-api.ts` and to `FleetStore` when it needs one. The live data is optional for every worker command: a failure there is a warning, never a failure, because Linear is the record.
- **The app's database is Postgres, one for everything** (`packages/dashboard/lib/db.ts`). Schema changes are new entries in `DB_MIGRATIONS`, never edits of an applied one; a test checks Better Auth finds every table and column it needs. Queries use `$1` parameters through `Database`/`Queryable` only, and work that must be atomic uses `transaction()` or one statement guarded by a unique index.
- **Tests earn their place.** One owner test per behaviour at the cheapest boundary; no network (use the recorded-fetch helper in `packages/core/test/support.ts`), no wall-clock waits (inject `now`). The CLI's side of the fleet runs against a fake API (`tempFleet()` and `fakeArmada()` in `packages/core/test/support.ts`, over `memoryFleet()`); the app's routes and store run on PGlite.
- **English** in code, CLI output, docs and tracker comments.
- **The published CLI is one Node bundle.** `bun build` inlines `core` and every dependency into `dist/armada.js`; the package has no runtime dependency. Code that runs in the CLI must work under Node 22 (no `Bun.*` APIs). A dependency that cannot be inlined (a native addon) goes in the build's `--external` list and in `packages/cli/package.json` `dependencies`; the tarball job in CI loads the whole bundle, so a missed one fails there.
- **Releases.** The CLI is published to npm as `@the-vibe-company/armada` by release-please (`.github/workflows/release.yml`). Pull request titles become the changelog: while in 0.x, `feat` and `fix` bump the patch version and a breaking change bumps the minor. After any merge that touches `packages/cli` or `packages/core`, the coordinator merges the open release pull request right away, so every change ships (continuous 0.x). Publishing uses npm Trusted Publishing; never add an npm token. If the publish job fails, fix the cause and re-run the failed jobs of that Release run: later pushes do not publish an already tagged version.
- Pull request titles follow Commitizen, for example `feat(cli): show the fleet state with armada status`.
- Work follows the fleet protocol: one ticket, one branch named after it, one pull request. Workers never merge.
