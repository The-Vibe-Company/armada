# Repository instructions

Armada v2 launches coding agents (Claude Code, Codex) through provider-scoped sandboxes: a remote MCP server for orchestrators, the dashboard and the API-only `armada` CLI. It is a launcher, not an orchestrator. The specification is issue #455; read it before changing behaviour.

Armada v1 (the fleet orchestrator) is archived at the tag `armada-v1-final`. Its code is not on `main`; bring a piece over by hand when v2 needs it (`git show armada-v1-final:<path>`), never by restoring whole folders.

## Layout

- `packages/core` (`@armada/core`): the shared contract (types, the version). No network or database I/O. Two entrypoints: `.` (`src/index.ts`) is genuinely safe for a browser bundle (the dashboard imports only this; type-only exports are fine, no file it reaches imports a node builtin), and `./server` (`src/server.ts`, everything `.` has plus the pieces that do: a child process, the filesystem, signing) is for `packages/mcp-server` and `packages/cli` only. `src/boat-snapshot-name.ts` is split out of `golden-config.ts` for exactly this reason (the only `node:crypto` use there) and is `./server`-only. `src/provider.ts` is the `Provider` interface (goldens, sandboxes, prompts, events by cursor), the common `AgentEvent` stream, per-harness capabilities and `ProviderError`. `src/golden-config.ts` is the versionable golden file (repos, branches, init; secret keys refused) and the namespaced boat snapshot name. `src/golden.ts` builds, connects and snapshots a golden through a `Provider` and a `GoldenStore`; `goldenForLaunch` is the lookup launch uses. `src/golden-store.ts` is that store over SQL, under the caller's database role. `src/crypto.ts` seals `*_enc` values with AES-256-GCM (`iv || ciphertext || tag`) under the single env name `ARMADA_ENCRYPTION_KEY`; the dashboard and credential resolution (#461) both call it. `src/credentials.ts` resolves credentials for a launch (user over org) and `src/vault.ts` holds the org, member and credential rules over a service-role `VaultStore`. `src/github.ts` is the GitHub identity of a launch: the App's user-to-server OAuth (code exchange, refresh with rotation by compare-and-swap, revocation), `resolveGitHubAccess` and the git setup command run in the sandbox. `github_connections` holds the sealed refresh token per user; setup in `docs/github-app.md`. The rest of this paragraph is `./server`-only. `src/golden-create-service.ts` (`GoldenCreateService`, `goldenScript`) coordinates the secure, disposable-builder path (`armada golden create`, `golden_create`): authorize, checkout, SSH clone, scan, snapshot, persist, always cleaning up the builder; `withGoldenDirs` assigns each repo the single-segment directory both the build script and the persisted config use. `src/golden-github.ts` (`goldenGitHubAdapter`) is its GitHub-facing half: authorization with the caller's own token, and an optional installation-token `mint` present only when `src/github-installation.ts` (`mintInstallationToken`, a GitHub App JWT and the one-hour installation token it mints and revokes) has signing credentials. `src/golden-scan.ts` is the fail-closed pre-snapshot secret grep (working tree and git history, filenames only, never a match). `src/skillpack.ts` is server-only: shared Skillpack install commands and verified receipts for sandbox launches and the orchestrator bootstrap. `src/ssh-executor.ts` (`sshStdinCheckout`) is the pinned, stdin-only SSH transport a scoped key never written to argv or disk. `src/golden-create.ts` (`createGoldenCreateService`) wires all of that to a real `Sql` and `GitHubResolveDeps`; `packages/mcp-server` and the control API both share one instance. `src/database.types.ts` is generated from the Supabase migrations (`bun run db:types`). `src/sandbox-provider.ts` keeps provider identity (`boat` or `modal`) and immutable Modal workspace/environment/App binding. Goldens and sandboxes carry neutral provider IDs; Boat-only compatibility aliases must stay null for Modal. A golden is built and saved separately for each provider.
- `supabase/migrations`: the Supabase CLI migrations. Schema first, then row level security. A fresh Supabase database already has `auth.users`, `auth.uid()` and the `authenticated` and `service_role` roles. `goldens.boat_sandbox_id` is the master sandbox; `boat_snapshot_id` is the namespaced saved-snapshot name, null until snapshot. `oauth_clients` and `oauth_codes` are the MCP authorization server, writable only as `service_role`. Supabase grants `ALL` on every new public table, sequence and function to `anon` and `authenticated`, and a column grant only adds to that; `20261108190000_revoke_default_grants.sql` revokes it (and those default privileges), so `anon` holds nothing and a new table or column is reachable by a user JWT only through an explicit grant. `scripts/db/supabase-prereq.sql` reproduces Supabase's defaults so the tests see them. A user JWT selects no `hash` or `*_enc` column (`20261108200000_token_hash_column_grants.sql` narrows the token tables), so any user-JWT request that writes a row names the columns it returns with `select=`: a bare PostgREST insert returns `*`.
- `packages/provider-boat` (`@armada/provider-boat`): the boat.dev provider adapter over `@boatdev/sdk` (`createBoatProvider`; `src/errors.ts` maps boat errors, `src/events.ts` normalizes events). `createGolden` always sends `noEnv: true` and never an account environment. Unit tests run the real SDK against a fake `fetch`; `test/integration.test.ts` is opt-in (`BOAT_API_KEY`).
- `packages/core` also holds the launch flow: `src/launch.ts` (`launchSandbox`), `src/credentials.ts` (user over org), `src/sandbox.ts` (the sandbox store and the cleanup) and `src/outcome.ts` (a prompt's final status). `src/sandbox-provider.ts` keeps provider identity (`boat` or `modal`) and immutable Modal workspace/environment/App binding. Goldens and sandboxes carry neutral provider IDs; Boat-only compatibility aliases must stay null for Modal. A golden is built and saved separately for each provider.
- Templates (API/MCP slice 4, no secret bindings): browser-safe `packages/core/src/templates.ts` defines preset DTOs and `readable-variables.ts` validates readable configuration; both are exported from `@armada/core` (`.`). Server-only `template-service.ts` owns immutable revision publication, reference authorization, durable idempotent launch claims/manifests and existing golden-operation fence adoption; `ssh-readable-variables.ts` is the fixed Boat SSH-stdin bootstrap, exported only from `./server`. Revisions store connection IDs; current connected grant versions/generations resolve into the frozen launch manifest, never at publication. The tables are `launch_templates`, `launch_template_revisions` and `template_launch_requests` (RLS/select-only user grants; service-owned writes). `LaunchOptions.beforeStart` performs final admission after init/MCP setup, then `Provider.configureReadableVariables` delivers only to the selected native harness (Modal private runner operation; Boat native-wrapper `/run` file). Boat's file is world-readable non-secret configuration: unrelated exec does not inherit its environment but can read it. Later-turn `mcp-lifecycle.ts` uses its existing authorized sandbox read to hint only template requests with readable values, then re-delivers the frozen manifest under current membership/sandbox access without consulting mutable template/reference versions. Non-template prompts incur no extra template-query round trips or SSH. See `docs/templates-staging.md` for API shapes, recovery limits and coordinator checks.
- `packages/auth` (`@armada/auth`): Supabase login, the MCP OAuth server, service tokens and bearer verification. Tokens are stored as lowercase sha-256 hex. The CLI keeps the Supabase session on the machine; the MCP server verifies bearers with the service role and does not cache them.
- `packages/cli` (`@armada/cli`): the API-only `armada` command. `src/run.ts` takes I/O as arguments; `src/armada-api.ts` authenticates requests to the Armada origin under `/api/v1/`. The terminal stores only its Armada session or uses `ARMADA_TOKEN`; it never connects to Supabase or holds provider/database credentials. Golden, sandbox, organization, credential and agent operations run through the same server policies used by the web and MCP surfaces. Model and reasoning effort are selected at launch and persisted for later turns.
- `packages/mcp-server` (`@armada/mcp-server`): the remote MCP server run by `armada-server`. `src/http.ts` is the handler (`/healthz`, the OAuth routes, the control API, `/mcp`), `src/tools.ts` the MCP tools, `src/turns.ts` the prompt status, wait and failure reason, `src/data.ts` the SQL reads and writes, which carry the visibility rule themselves because the server's connection bypasses row level security. `src/control.ts` is the control API for `armada org`, `armada creds`, credential resolution at launch and `golden/create` (`handleControlRequest`, mounted in `armada-server`). `golden_create` in `src/tools.ts` and `golden/create` in `src/control.ts` share one `GoldenCreateService` built in `src/serve.ts` by `@armada/core`'s `createGoldenCreateService`. Tests drive it through the MCP SDK client on PGlite with the real migrations and a fake boat. `Dockerfile` (needs `openssh-client`, for `golden_create`'s SSH checkout) and `railway.json` deploy it.
- `apps/dashboard` (`@armada/dashboard`): the web dashboard (Next.js App Router, Tailwind, shadcn/ui). It acts as the signed-in user over Supabase (RLS applies), never with a service key. Pure logic lives in `src/lib` (tested with `bun test` in `test/`); `e2e/` is Playwright against `e2e/mock-supabase.ts`. Writes RLS cannot express go through the functions of `supabase/migrations/*_dashboard_functions.sql`. A page's create/add flow is `src/components/create-dialog.tsx` (`CreateDialog`, #896): a header button passed as `ResourceBrowser`'s `actions` opening one short form in a centred dialog, never a side panel; what the page already lists is not repeated in it.
- `scripts/build.ts`: compiles the binary with `bun build --compile` (linux and macOS, x64 and arm64).
- `scripts/npm.ts` stages the npm packages from those binaries: `@the-vibe-company/armada` (the `armada` bin, the Node launcher `packages/cli/npm/armada.cjs`) and one `@the-vibe-company/armada-<target>` per binary, as optional dependencies. `scripts/npm-smoke.sh` installs the packed tarballs with npm and Bun and runs them. `.github/workflows/release.yml` runs Release Please on `main`, synchronizes Bun’s lockfile and dispatches CI for the version PR, then builds and publishes through npm OIDC when that PR merges; manual runs support dry runs and tagged recovery (`docs/releasing.md`). `docs/dave-onboarding.md` is the production onboarding guide.

## Commands

- `bun install`
- `bun scripts/prepare-runtime.ts`: prepare the portable runtime before local server tests. Linux CI builds and validates the native runtime with `bun packages/agent-runtime/build.ts` and `bun scripts/validate-runtime-native.ts` instead.
- `bun run verify`: lint (Biome), typecheck (`tsc`, strict) and tests (`bun test`). CI runs the same as "Lint, typecheck and test".
- `bun run format`: apply Biome formatting and safe fixes.
- `bun run build` (this machine), `bun run build --target <os-arch>`, `bun run build:all`: the binary in `dist/`.
- `bun run armada <args>`: the CLI from source.
- `bun run dashboard`, `bun run dashboard:build`, `bun run e2e`: the dashboard (dev, production build, browser tests). `bun run verify` typechecks it and runs its unit tests, not the e2e.
- `bun run db:types`: regenerate `packages/core/src/database.types.ts` after a migration change.
- `scripts/aeom/install.sh`: install All Eyes On Me at its pinned commit to redesign or review the public landing (`.aeom/`, `docs/aeom.md`).

## Rules

- **Separate client and server.** `armada` is an API-only client; `armada-server` contains the server and provider/database adapters. Both compile with Bun. Never import Supabase, provider implementations or server startup into the CLI runtime dependency graph.
- **One version.** Every `packages/*/package.json` carries the same version; `@armada/core` exports it and `armada --version` prints it.
- **Secrets never in the repository.** Keys come from the environment or Armada's encrypted store; never print one, never write one into a file, a fixture or a log. Goldens hold no secrets. In the database a secret is ciphertext (`bytea`, `*_enc`) or a token hash, and a user JWT cannot read the ciphertext columns. One encryption scheme: `encryptSecret` and `decryptSecret` in `@armada/core` with `ARMADA_ENCRYPTION_KEY`. Credential values arrive on stdin or from a file, never as arguments.
- **Schema changes are new migrations.** Never edit a migration that has been applied. Row level security is the access rule: members see org resources, a private resource is visible only to its owner, and only an admin changes an org golden, the members or an org key.
- **Tests earn their place.** One test per behaviour at the cheapest boundary, no network, no wall-clock waits.
- **English** in code, CLI output, docs and comments.
- Pull request titles follow Commitizen, for example `feat(cli): launch an agent from a golden`.
