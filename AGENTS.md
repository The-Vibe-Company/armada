# Repository instructions

Armada runs a fleet of coding agents on one project: Linear holds the plan and progress, GitHub holds the code, and the `armada` CLI gives the coordinator and the workers one shared reading of the fleet.

## Layout

- `packages/core`: `armada.toml` parsing, read adapters for Linear and GitHub, the one Linear write adapter (`linear-write.ts`, behind `LinearWriter`; tests use `FakeLinear` in `test/support.ts`), the fleet's live data (`live.ts`: the records, the `FleetStore` the app implements, what each command records and the inbox read; `fleet-api.ts`: both halves of `POST /api/cli/fleet/<operation>`, the CLI's `fleetClient` and the app's `serveFleet`, which checks each request and a worker session's scope), the machine store (`machine.ts`: keys, personal defaults, each project's watch state and the Armada releases a coordinator was told of under `~/.config/armada`), the pure fleet derivations (tickets in flight, frontier, pull requests waiting; `activity.ts`: an agent's history from its comments, events and inbox, THE-869; `insights.ts`: how fast the fleet ships and where tickets wait, THE-893) and phase rules (`phases.ts`, with the plan rule: `[policy] plans` and its per-ticket labels), the worker commands (`worker.ts`: claim, report, release), questions and the coordinator's inbox (`inbox.ts`: ask, inbox, answer), the coordinator's watch (`watch.ts`: the `armada watch` loop, the re-arm line every coordinator command ends on, the Claude Code stop hook's decision), the dashboard's requests (`requests.ts`: answer and launch requests, checked before they are written), the launch brief (`brief.ts`; the CLI reads the `[brief] extra` file it ends with) and the profile routing it and `claim` share (`routing.ts`: `[[conductor.routing]]` on the ticket's labels, `--profile` overrides with a reason), the coordinator's merge (`merge.ts`: checklist, fresh-main retest, merge lease, pinned merge behind the `MergeForge` and `LocalRepo` adapters; `queue-drain.ts`: serial durable merge queue execution, lease renewal, hold waits, bounded retries and confirmed-merge recovery), what the owner validates (THE-885: `validations.ts`, the merge approval rule, `[[policy.validation]]` judged at launch, the owner's decisions; `validate.ts`: `armada validate`, `ask-owner`, `done`), the Armada API client (`armada-api.ts`: `armada login`'s device code and polling, whoami, sign-out, the organization's Linear key, the organization's projects, the fleet operations; the address and the sign-in resolve in `credentials.ts`), and the repository setup rules shared by `doctor` and `init` (`setup.ts` over a read-only `RepoView`, `labels.ts` for the Linear label groups, `skills.ts` for the bundled skills). No I/O outside the adapters; network adapters take an injected `fetch` and share `http.ts`'s bounded retry rule for safe reads and guarded/idempotent writes, with injected waits and retry notices.
- `packages/cli`: the `armada` command. The runtime interface is `core/src/runtime.ts` (names, states, claim references, errors, delivery keys) and `src/runtimes/` (the registry and adapters for Conductor, herdr and guided Claude Code); `src/runtime.ts` publishes observations, delivers and stops through it. Side effects are injected through `Io` in `src/io.ts`; `src/main.ts` wires the real process; `src/bin.ts` is the entry of the published Node bundle.
- `packages/dashboard`: the live Fleet view (Next.js App Router), not published to npm. One Postgres database (Neon in production, PGlite in tests and local development) holds everything the app keeps: `lib/db.ts` (the `Database` interface over node-postgres or PGlite, `DB_MIGRATIONS` applied under an advisory lock, never Better Auth's automatic migration; `ARMADA_DATABASE_URL`), opened once per process by `lib/app-db.ts`; the fleet's live data is `lib/fleet-store.ts` (registry, events, runtime handles, inbox, leases with `SELECT ... FOR UPDATE`, coordinator presence). `lib/fleet-data.ts` orchestrates reads behind an injected `Sources` (THE-853): a page or poll reads Postgres only, each project's last reading of Linear and GitHub (`lib/snapshots.ts`: `fleet_snapshots`, versioned bodies each server keeps, a per-project lease, the webhooks' marks) and the fleet store; a missing, stale or marked reading is refreshed after the response (`after()`, `refreshProject`: core's incremental `refreshStatusSources`, whole every 30 minutes). `lib/webhooks.ts` (routed at `/api/webhooks/linear|github`, which both gates let through) verifies Linear's and the GitHub App's deliveries (`ARMADA_LINEAR_WEBHOOK_SECRET`, `ARMADA_GITHUB_WEBHOOK_SECRET`), marks the readings they concern and has them refreshed after the answer; `lib/live-http.ts` gives the live route `/api/fleet` its ETag and 304, without the timeline's history (core reads each row's step from it; no screen draws it since THE-1020); `lib/server.ts` wires the environment; every page of the shell follows the v7 design's anatomy (THE-1021: the `pg-*` classes, a line of facts, a 22 px title and a quiet line, then the page's blocks) and shares the page kit, `components/page.tsx` (THE-876: `PageHeader` drawn by the shell, `HeaderActions`, `Alert`, `Notice`, `PageSkeleton`, and the form controls `Form`, `Input`, `Select`, `Button` (THE-871)); the organization's pages share `components/org.tsx` (tabs, a hint beside one action, four-column rows, "Manage" disclosures); `test/page-anatomy.test.ts` refuses an `h1` or a font other than Geist and Geist Mono under `app/(fleet)` and `app/organization`, and a class `globals.css` styles that nothing renders (the second class of `.a.b` too); the pages before the shell (sign in, welcome, device, invitation) share `components/AuthCard.tsx`; every fleet rule stays in core (`buildStatus`, `buildOverview` in `overview.ts`), imported through `@armada/core/read`, which leaves out the Bun-only skill imports. `lib/cli-api.ts` (routed at `/api/cli/*`, which both gates let through) is the API the CLI calls: device authorization for `armada login` (confirmed on `/device`), whoami, sign-out, `POST credentials`, `GET projects` and `POST fleet/<operation>` (every read and write of the fleet's live data: core's `serveFleet` on `fleetStore`, for a project the caller's organization holds, registered for it on first contact), with a session token, an organization API key or a worker session. Every answer names the oldest CLI that reads it right (`MINIMUM_CLI_VERSION` in core's `armada-api.ts`: raise it with a breaking change to an answer) and the latest one; an older CLI prints one upgrade line instead. No terminal holds a database key. The vault (THE-840): `lib/vault.ts` seals the organization's keys (AES-256-GCM envelope under `ARMADA_SECRETS_KEY`) in the app's database and keeps their audit list; each project keeps its own too (THE-859: a Linear key that wins for it, and secrets for workers, `OPENAI_API_KEY`, which `secrets/<operation>` of `lib/cli-api.ts` lists, releases, sets and unsets; an organization API key acts with its creator's role of today); `lib/broker.ts` hands the Linear key to terminals and the Linear and GitHub keys to the dashboard's own reads (`lib/server.ts`, per organization; only the first organization falls back to the environment's); the Keys page is `app/organization/keys` with `app/keys-actions.ts`. GitHub (THE-851): `lib/github-app.ts` is the Armada GitHub App (`ARMADA_GITHUB_APP_ID`, `ARMADA_GITHUB_APP_PRIVATE_KEY`): an app JWT, the installation covering each repository, installation tokens minted server-side and cached until near expiry; every GitHub read of the dashboard goes through it (`lib/server.ts`), a stored GitHub token only as fallback. The first organization reads through any installation, another only through those an owner or admin linked on `app/organization/github` (`app/github-actions.ts`), after GitHub listed them for that person; that page is also the app's Setup URL (THE-852, `lib/github-install.ts`): its Install on GitHub button (`app/organization/github/install`) signs a short-lived, single-use state, and GitHub's return is handed to `app/organization/github/setup`, where `linkFromSetup` links the installation under the same rule (`linkForViewer`, shared with the Link button); the same app's client id and secret sign people in. Workers (THE-841): `lib/workers.ts` keeps the one-time launch tokens `armada brief` asks for (`POST /api/cli/launch-tokens`: one ticket, used once, one hour, stored hashed) and the worker sessions they are exchanged for (`launch-tokens/exchange`, rate-limited per address); a worker session only gets keys and fleet operations for `claim`, `report`, `ask` and `release` on its own ticket and project, and ends on release, merge (`workers/end`) or Revoke on `app/organization/workers` (`app/workers-actions.ts`). Fleet writes are `lib/requests.ts` and `app/actions.ts` only: requests to the coordinator's inbox (answer, launch), checked by `core/requests.ts` over its `RequestStore`, never a runtime call. The public landing (THE-887) is `app/landing` (prerendered, `force-static`, no cookie, database, Linear or GitHub read): the proxy rewrites `/` to it for a viewer without a session (`isFront`, `LANDING_PATH` in `lib/accounts-settings.ts`; no session lookup without a session cookie) and lets `/landing/*` through; its sections are `components/landing/` (`flock.ts` the hero's flock, stepped by frame time; `Replica.tsx` the dashboard's own sidebar and overview, `Sidebar` and `Overview` of `OverviewScreen.tsx` on no filter, in `ShowcaseProvider`, playing `lib/demo/overview.ts` from the static `/landing/fleet.json` through `replica-script.ts`, ending on a session waiting for the owner's decision, THE-931); `bun run landing` (`scripts/landing.ts`) writes its terminal from the CLI's own renderers and its share image, and `test/landing.test.ts` fails until then and holds its claims to the code. The root layout is static so the landing can be: the pages that read the language cookie set `<html lang>` through `components/DocumentLanguage.tsx`. `scripts/db.ts` (`bun run db migrate|register`) applies the schema and registers a project from a terminal. The owner's validations (THE-885) are the `validations` table of `lib/fleet-store.ts`, decided by `decideValidation` in `app/actions.ts` (a `decision` item in the coordinator's inbox), shown on `/validations` and `/approve/<id>` (the link the CLI prints, readable at 375 px; Validations is in the menu since THE-1020), as a list beside the selected one (`/approve/<id>` selects it; on a phone the list and the validation are two pages; `components/screens/ValidationCard.tsx`: what to check and why, the pull request in one strip, its images in one strip, full screen on a click, the arrow keys between them, a note and the owner's buttons). The keys decide the selected one (THE-1113, `lib/validation-keys.ts`, a pure reducer: A approves, C puts the focus in the note and ⌘↵ sends the changes, 1–6 pick a choice; never in a field), the next waiting one opens once recorded, and the list's head says about how long those waiting take (the median gap between two decisions by the same person at most ten minutes apart, from three such gaps). The shell and the overview (THE-1020) are the owner's v7 design (`design/dashboard-v7`): the sidebar (`components/shell/Sidebar.tsx`: the mark, the organization, a search field that opens ⌘K, Overview and Validations with their counts, Activity, Insights, one line per project with its coordinator's diamond and what is blocked in it, the organization, the live reading) and `components/screens/OverviewScreen.tsx` at `/`: one headline of what is blocked and what waits for the owner, a card per project, then every session in flight and every ticket merged on the viewer's day (`armada-tz`) in one list grouped by state (blocked, waiting for your decision, in progress, ready to merge, merged today) or by project, each row with its reason in its state's color and a six-step bar; the rules are `lib/coordinator-view.ts` (`sessionState`, `sessionStep` from the phase and core's `flowStep`, THE-987's shipping stage, `overviewItems`), and the view lives in the address (`?coordinator=` a project, `?owner=` a named coordinator's sessions (THE-1112), `?group=project`, `?view=preview`, `?ticket=`; older parameters are ignored, `/agents` redirects there). ## Commands

- `bun install`
- `bun run verify`: lint (Biome), typecheck (`tsc`) and tests (`bun test`). CI runs the same on every pull request.
- `bun run format`: apply Biome formatting and safe fixes.
- `cd packages/cli && npm pack`: build `dist/armada.js` (Bun bundles `core` for Node) and pack the npm tarball. CI installs that tarball and runs it on every pull request.
- `cd packages/dashboard && ARMADA_DASHBOARD_PASSWORD=off bun run dev`: the dashboard on port 4822 (`off` works outside production only; without it or accounts every route answers 503); `bun run build` is the Vercel build and runs in CI. `bun run perf bundles|lighthouse|inp|report` checks the performance budgets against a production build (`docs/performance.md`). See the README for the demo mode and for running it with accounts (`ARMADA_DATABASE_URL=pglite:.demo/armada`, a local PGlite database). Dashboard tests run on PGlite; `ARMADA_TEST_DATABASE_URL` (a direct URL to a throwaway Neon branch, never production) runs the same tests on real Postgres, one schema per test file.
- From any folder, `ARMADA_CONFIG=/path/to/armada.toml` or `--project <slug>` selects a project (the latter uses this machine’s last watched checkout); `--config <path>` overrides both.
- `bun run armada status [--json]`: runs the CLI from source; needs `LINEAR_API_KEY`; GitHub uses `GITHUB_TOKEN`, `GH_TOKEN` or `gh auth token`.
- `bun run armada auth login|status|logout`: keys stored once per machine in `~/.config/armada/credentials`; `auth status` shows the key source and last Armada keys failure (local fallback retries after five minutes and warns once an hour).
- `bun run armada login [--api-key]`, `whoami [--json]`, `logout`: sign this terminal in to Armada (`ARMADA_API_URL` points it at a local dashboard with accounts, e.g. `http://localhost:4822`). `armada login --launch-token <token> [--api-url <url>]` is a worker's first authenticated command: the token comes from the launch message `armada brief` prints when the coordinator is signed in; the worker session is kept per ticket (`ARMADA_WORKER_SESSION_<TICKET>` in the credentials file).
- `bun run armada secrets [set|unset|get|export]` and `bun run armada run -- <command>`: a project's secrets for workers (THE-859), through Armada; `run` first, `export --file` for dotenv tools, `get` for a person only.
- `bun run armada claim|report|release|ask`: the worker commands; their live record goes through Armada when the terminal is signed in (`ARMADA_API_URL=http://localhost:4822` for a local dashboard with accounts), and is skipped with a warning otherwise.
- `bun run armada peek <ticket> [--actions <n>] [--json]`: coordinator-only worker inspection: runtime state, reply, recent commands, report/heartbeat, PR checks and open questions; local `TZ`, masked secrets, bounded incremental transcript reads. Includes bound launches before claim; publishes Armada observations and never writes to the runtime.
- `bun run armada watch`: the coordinator's background watch; `--follow` streams resumable lines (NDJSON with `--json`), `--since <cursor>`, `--tickets` and `--kinds` filter it, and `--for <minutes>` bounds either mode with a resume command. Use follow only where every line reaches the agent; it shares plain watch's lock and `--stop`. Plain watch exits when something needs the coordinator (a required CLI/setup upgrade too, as a `version` item) or nothing is in flight. `status` and `inbox` announce ordinary releases on stderr at most once per 24 hours per machine (`packages/cli/src/release.ts`); only required CLI/setup upgrades stop either watch mode. `armada upgrade` verifies npm publication and the installed CLI, then runs `armada init --merge` only for outdated setup. `armada hook stop` is the Claude Code Stop hook `init` installs (`ARMADA_STOP_HOOK=off` turns it off).
- `bun run armada inbox [--wait]` and `bun run armada answer <item|ticket> "<text>" [--note]`: the coordinator's inbox (through Armada; `--wait` asks every 15 s and Armada answers 304 while it is unchanged) and how it records an answer it already delivered through the runtime guide. `answer` delivers herdr and Conductor answers and notes automatically before recording, with a stable Conductor message id for retries; Claude Code answers are delivered through their guide first. `armada stop <ticket>` archives a herdr worktree only when clean and fully pushed.
- `bun run armada hold [--json]`, `hold add "<reason>"`, `hold clear <id> --reason "<why>"`: the project's shared persistent merge pauses. Status, watch and inbox show them until cleared. A fix uses `armada merge <pr> --through-hold "<why>"`, recorded with every hold id; `--no-lock` skips both the lease and hold read.

- `bun run armada ci why <pr|url> [--rerun] [--json]`, or `ci why --sha <sha>` / `ci why --branch <branch>`: explain failed checks, test names, first error lines and runner problems. Needs a GitHub token only; Actions read gives job logs. Optional `[ci] failure_patterns` holds regex strings with exactly one capture group for a test name. `[[ci.known_failure]]` requires an exact `check`, regex `pattern` and root-cause `ticket`. `--rerun` reruns failed jobs once per completed first-attempt workflow run only when every failure is known or a runner problem, and names the flaky tickets; unknown/external failures and incomplete evidence are refused. GitHub supplies the attempt count; no force override.
- `bun run armada merge <pr> --dry-run`: the coordinator's merge checklist without merging. Never run `armada merge` without `--dry-run` from a worker: workers never merge. Archive only after the final `Result: merged #N` confirms the merge. Linear outages use an exact Armada hand-back; the confirmed merge is recorded on Armada before Linear, and `armada merge --finish <pr>` completes any visible `linear-pending` inbox chore. The coordinator adds `--wait [--timeout <min>]` when main keeps moving (update branch on GitHub, wait for the checks, merge the hand-back with main merged in) and `--no-ticket` for a pull request no ticket owns (`armada init`'s, a release).
- `bun run armada launch <ticket> [--runtime conductor|herdr] [--profile <name> --reason "<why>"] [--notes <file|->] [--dry-run] [--json]`: launch one worker through the shared runtime adapter. Runtime follows the chosen profile. Checks and notes (up to 16 KB) precede token creation; a per-ticket lease prevents duplicate launches. Conductor receives its brief through stdin; output names the handle and link, never the token. Known failures revoke the exact token; unknown outcomes are recovered without retrying create. Claude Code profiles point to the Agent tool and `armada brief --prompt`.
- `bun run armada brief <ticket> [--profile <name>] [--prompt|--json]`: a worker's launch prompt and settings; needs `LINEAR_API_KEY`.
- `bun run armada doctor [--json]` and `bun run armada init [--program-root <ID>]`: check a repository (and whether this terminal is signed in to Armada), and open its setup pull request. Try `init` only on a throwaway repository: it pushes a branch, opens a pull request and creates Linear labels.

## Rules

- **Generic and open source.** No customer or private project names, data, thresholds or recorded responses. Fixtures are synthetic: invented ticket ids, titles and people.
- **Everything project-specific comes from `armada.toml`.** Program root, repository, label names and thresholds are configuration, never constants.
- **Secrets from the environment, Armada or the machine store, resolved in one place.** `resolveCredentials` in `packages/core/src/credentials.ts` picks each key (environment first, then the organization's keys from Armada when signed in, then `~/.config/armada/credentials`); only `packages/core/src/machine.ts` reads or writes that file. A secret stored by the dashboard goes through `lib/vault.ts` only, sealed, and no page or log ever receives its value. Never read tokens anywhere else, never print one, and never write one into a repository file, a fixture or a log. Tests point `XDG_CONFIG_HOME` at a temporary directory, never at the real one.
- **The CLI reaches the fleet's live data only through the Armada API** (`fleet-api.ts`), with the terminal's sign-in; no machine holds a database key. Every operation answers from Postgres with indexed queries, holds nothing open (no long poll: a waiting client polls, and gets 304 when nothing changed) and never calls Linear or GitHub. Every row carries its project slug, leases are scoped per project, and times are the server's. Named coordinator roles and their session presence live in `coordinators` and `coordinator_sessions`; worker ownership comes from the authenticated launch, never the worker request. Handover updates ownership atomically and records a `handover` event without changing phase or liveness. Machine watch state and locks are scoped by project and coordinator name (`default` keeps the old filenames). A new operation is added to both halves of `fleet-api.ts` and to `FleetStore` when it needs one. The live data is optional for every worker command: a failure there is a warning, never a failure, because Linear is the record.
- **No page or poll calls Linear or GitHub.** Pages and `/api/fleet` read Postgres only; Linear and GitHub are read after the response (`after()`), on a stale or webhook-marked reading, never on a timer. A test makes every Linear and GitHub read hang and checks that the pages still answer.
- **The app's database is Postgres, one for everything** (`packages/dashboard/lib/db.ts`). Schema changes are new entries in `DB_MIGRATIONS`, never edits of an applied one; a test checks Better Auth finds every table and column it needs. Queries use `$1` parameters through `Database`/`Queryable` only, and work that must be atomic uses `transaction()` or one statement guarded by a unique index.
- **Tests earn their place.** One owner test per behaviour at the cheapest boundary; parser cases belong in core/config and reexport cases in their original owner. Each negative must exercise its own operation and assert the positive prerequisite before the forbidden result; never borrow earlier cases' logs, rows or tokens; no network (use the recorded-fetch helper in `packages/core/test/support.ts`), no wall-clock waits (inject `now`). The CLI's side of the fleet runs against a fake API (`tempFleet()` and `fakeArmada()` in `packages/core/test/support.ts`, over `memoryFleet()`); the app's routes and store run on PGlite.
- **English** in code, CLI output, docs and tracker comments.
- **The published CLI is one Node bundle.** `bun build` inlines `core` and every dependency into `dist/armada.js`; the package has no runtime dependency. Code that runs in the CLI must work under Node 22 (no `Bun.*` APIs). A dependency that cannot be inlined (a native addon) goes in the build's `--external` list and in `packages/cli/package.json` `dependencies`; the tarball job in CI loads the whole bundle, so a missed one fails there.
- **Releases.** The CLI is published to npm as `@the-vibe-company/armada` by release-please (`.github/workflows/release.yml`). Pull request titles become the changelog: while in 0.x, `feat` and `fix` bump the patch version and a breaking change bumps the minor. Leave the release pull request open after each merge: the release train merges it once each weekday at 07:00 UTC (Monday to Friday), carrying everything merged since the last release, and tags and publishes in the same run. For an urgent fix, run `gh workflow run release.yml` to release at once. Publishing uses npm Trusted Publishing; never add an npm token. If the publish job fails, fix the cause and re-run the failed jobs of that Release run: later pushes do not publish an already tagged version.
- Pull request titles follow Commitizen, for example `feat(cli): show the fleet state with armada status`.
- **Runtime actions target one worker generation** (THE-1074). Use `runtimeFor(io, config, runtime)` and `guarded(fleet, ref, "active" | "ended", () => adapter.deliver/cancel/archive(...))`; adapters refuse mutations outside the guard and re-read the claim after provenance checks before every native write. `ClaimRef` includes the canonical handle, claimed/released timestamps and worker-session launch id; its optional branch carries herdr provenance. `observe`/`peek` are read-only. Prompts/messages use `Exec.input` for Conductor, and the existing single argv item for herdr. Never print runtime output or retry a write of unknown outcome. Conductor observations are throttled to one attempt per handle/generation per minute in the machine watch state; dashboard pages only read the stored state. Conductor archives require release or merge; herdr retains its historical clean-and-pushed active stop. Migration 23 adds `failed`/`gone`; deploy the dashboard before the new CLI. `HerdrAdapter.launchPrepared` preserves the legacy brief's need for its newly created handle; new runtime callers use `launch(spec)`.
- Work follows the fleet protocol: one ticket, one branch named after it, one pull request. Workers never merge.
